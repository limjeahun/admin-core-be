# Admin Core DDD·헥사고날 아키텍처 가이드

## 1. 전체 아키텍처와 의존성 방향

```text
HTTP 요청 / Security Filter
            │
            ▼
┌────────────────────────────────────────────┐
│ Input Adapter                              │
│ adapter.in.web / adapter.in.security       │
└───────────────────┬────────────────────────┘
                    │ Application이 정의한 Input Port 호출
                    ▼
┌────────────────────────────────────────────┐
│ Application                                │
│ application.port.in / service / port.out   │
└───────────────────┬────────────────────────┘
                    │ Domain 행위 호출
                    ▼
┌────────────────────────────────────────────┐
│ Domain                                     │
│ domain.model / domain.exception            │
└────────────────────────────────────────────┘

Application이 정의한 Output Port
                    ▲
                    │ 구현
┌───────────────────┴────────────────────────┐
│ Output Adapter                             │
│ JPA / Redis / JWT / BCrypt / Excel         │
└────────────────────────────────────────────┘
```

의존성은 바깥쪽 기술에서 안쪽 업무 규칙을 향한다.

```text
adapter.in  ──► application ──► domain
adapter.out ──► application ──► domain
config      ──► 필요한 구성 요소
```

반대 방향 의존은 허용하지 않는다.

```text
domain     ─X─► application
domain     ─X─► adapter
application─X─► adapter
application─X─► JPA, Redis, Spring MVC 구현 클래스
```

현재 소스 구조도 이 방향을 따른다.

```text
com.espay.admincore
├─ adapter
│  ├─ in
│  │  ├─ web
│  │  └─ security
│  └─ out
│     ├─ persistence
│     └─ redis
├─ application
│  ├─ dto
│  ├─ exception
│  ├─ port
│  │  ├─ in
│  │  └─ out
│  └─ service
├─ domain
│  ├─ exception
│  └─ model
├─ common
└─ config
```

### 개발 규칙

- `domain`은 Java와 같은 Domain 타입에만 의존한다.
- `application`은 Domain과 자신이 선언한 Port에 의존한다.
- `application`에서 허용하는 Spring 의존성은 현재 `@Service`, `@Transactional`뿐이다.
- `adapter.in`은 외부 요청을 Application 입력으로 변환한다.
- `adapter.out`은 Application이 선언한 Output Port를 기술 코드로 구현한다.
- JPA Entity, Redis Entity, Servlet 객체, Spring Security 객체를 Domain에 전달하지 않는다.
- `config`에는 Spring Bean, Security, CORS 같은 실행 환경 설정만 둔다. 업무 규칙을 넣지 않는다.

`application.yml`은 `SPRING_MAIL_*` 환경 변수를 `spring.mail.*`로 바인딩한다. `config.MailConfig`는 이 설정에 SMTP
인증, STARTTLS와 TLS 1.2를 적용한 `JavaMailSenderImpl` 빈을 생성한다. SMTP 클라이언트 생성은 외부 메일 서버 연결을
위한 실행 환경 설정이므로 `config`에 두고, 실제 OTP 안내 메일 작성과 발송은 Output Adapter인
`adapter.out.mail.SmtpOtpMailAdapter`가 맡는다. 특정 팀의 SMTP 접속값은 Config나 YAML에 하드코딩하지 않는다.

### 이 규칙의 근거

Alistair Cockburn의 **「Hexagonal Architecture」** 원문에서 애플리케이션은 UI나 데이터베이스 같은 외부 장치의 종류를 알지 않아야 하며, Adapter가 외부 입력을 애플리케이션이 이해하는 형태로 바꾼다고 설명한다. 이 내용 때문에 Controller와 JPA Repository가 Application 내부가 아니라 Adapter에 위치한다. [Alistair Cockburn의 원문](https://alistair.cockburn.us/hexagonal-architecture)

Robert C. Martin의 **『Clean Architecture』 22장 「The Clean Architecture」에** 나오는 Dependency Rule은 소스 코드 의존성이 고수준 정책이 있는 안쪽을 향해야 한다는 규칙이다. DB와 Web은 세부 기술이고 업무 규칙이 고수준 정책이므로 `application → adapter` 의존을 금지한다. [공식 Dependency Rule 장 발췌](https://www.informit.com/articles/article.aspx?p=2832399)

Eric Evans의 **『Domain-Driven Design』 4장 「Isolating the Domain」에** 나오는 Layered Architecture는 Domain Model이 UI, Application, Infrastructure 책임과 섞이지 않아야 모델의 의미를 유지할 수 있다고 설명한다. 이 내용 때문에 `domain.model`에 Spring, JPA, HTTP Annotation을 넣지 않는다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

## 2. 계층별 책임

### Domain

Domain은 업무 상태와 업무 규칙을 표현한다.

현재 예시는 다음과 같다.

```text
domain.model
├─ file
│  └─ FileHistory
├─ history
│  └─ LoginHistory
├─ menu
│  ├─ AdminMenu
│  └─ MenuPermissionAction
├─ role
│  ├─ AdminRole
│  └─ RoleMenuPermission
└─ user
   ├─ AdminUser
   └─ UserStatus
```

```java
public void validateLoginAllowed() {
    if (!isActive()) {
        throw new InactiveUserException(id);
    }
}
```

사용자의 활성 상태는 `AdminUser` 자신의 상태만으로 판단할 수 있으므로 Domain 행위다.

### Application

Application은 하나의 유스케이스를 완료하기 위해 Domain과 여러 Output Port를 어떤 순서로 호출할지 조정한다.

```java
@Service
@RequiredArgsConstructor
public class LoginService implements LoginUseCase {
    private final UserLookupPort userLookupPort;
    private final RolePersistencePort rolePersistencePort;
    private final PasswordHashPort passwordHashPort;
    private final PreAuthTokenPort preAuthTokenPort;
    private final PreAuthStatePort preAuthStatePort;
    private final LoginHistoryPersistencePort loginHistoryPersistencePort;
}
```

`LoginService`는 다음 순서를 담당한다.

1. 사용자를 조회한다.
2. 사용자와 권한의 로그인 가능 상태를 검증한다.
3. 비밀번호를 비교한다.
4. OTP 단계의 사전 인증 토큰을 발급한다.
5. Redis에 사전 인증 상태를 저장한다.
6. 로그인 이력을 저장한다.

사용자 상태 판단은 `AdminUser`, 권한 상태 판단은 `AdminRole`, 전체 로그인 순서는 `LoginService`가 맡는다.

### Input Adapter

Input Adapter는 HTTP와 Spring Security 형식을 Application 형식으로 바꾼다.

```text
adapter.in
├─ web
│  ├─ auth
│  ├─ user
│  ├─ role
│  ├─ menu
│  └─ history
└─ security
   ├─ authentication
   └─ authorization
```

Controller는 JSON, Header, Cookie를 받고 Input Port를 호출한다. Security Filter는 Authorization Header를 읽고 인증 Input Port를 호출한다.

### Output Adapter

Output Adapter는 Application이 요구한 기능을 기술 코드로 구현한다.

```text
adapter.out
├─ persistence
│  ├─ user
│  ├─ role
│  └─ history
└─ redis
   ├─ entity
   ├─ mapper
   └─ repository
```

예를 들어 `UserPersistencePort`는 Application의 계약이고 `UserPersistenceAdapter`는 JPA를 사용한 구현이다.

## 3. 업무 단위 패키지 규칙

Application Service와 Domain Model은 업무 단위로 나눈다.

```text
application.service
├─ auth
│  ├─ AccessTokenAuthenticationService
│  ├─ LoginService
│  ├─ OtpEnrollmentService
│  ├─ OtpVerificationService
│  └─ TokenSessionService
├─ history
│  ├─ HistoryService
│  └─ HistoryExportService
├─ menu
│  ├─ MenuService
│  └─ MenuPermissionAuthorizationService
├─ role
│  └─ RoleService
└─ user
   ├─ UserService
   └─ UserExportService
```

```text
domain.model
├─ file
├─ history
├─ menu
├─ role
└─ user
```

### 개발 규칙

- 새 클래스는 먼저 `auth`, `user`, `role`, `menu`, `history`, `file` 중 소유 업무를 결정한다.
- 전체 서비스를 `service.impl`에 모으지 않는다.
- 전체 모델을 하나의 `domain.model` 바로 아래에 평면적으로 두지 않는다.
- Request와 Response도 `adapter.in.web.auth`, `adapter.in.web.user`처럼 HTTP 업무별로 둔다.
- 여러 업무의 Response를 `adapter.in.web.response` 같은 전역 패키지에 모으지 않는다.
- 소유 업무가 불분명한 `util`, `helper`, `manager` 패키지를 먼저 만들지 않는다.

### 이 규칙의 근거

Eric Evans의 **『Domain-Driven Design』 5장 「A Model Expressed in Software」의 Modules 패턴**은 Module의 이름이 모델의 개념을 전달해야 하고, 관련 개념은 높은 응집도로 묶으며 다른 Module과의 결합은 낮춰야 한다고 설명한다. 이 내용 때문에 기술 종류만 나타내는 `service.impl`보다 `service.auth`, `service.user`처럼 업무 용어를 패키지명으로 사용한다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Vaughn Vernon의 **『Implementing Domain-Driven Design』 9장 「Modules」도** Module을 단순한 폴더 정리가 아니라 모델을 설명하는 수단으로 다룬다. 업무 변경 시 관련 Service와 Domain을 빠르게 찾을 수 있도록 현재 패키지를 업무 단위로 나눈 근거다. [공식 도서 페이지](https://www.informit.com/store/implementing-domain-driven-design-9780133039894)

## 4. 계층별 DTO 분리

로그인 요청 하나도 모든 계층에서 같은 객체를 사용하지 않는다.

```text
HTTP JSON
   ▼
LoginRequest                         Input Adapter DTO
   │ toCommand(clientIp, userAgent)
   ▼
LoginCommand                         Application 입력 DTO
   │ LoginUseCase.login(...)
   ▼
LoginChallengeResult / LoginResult   Application 결과 DTO
   │ LoginResponse.from(...)
   ▼
LoginResponse                        Input Adapter의 HTTP 응답 DTO
```

영속성 흐름도 Domain과 JPA Entity를 분리한다.

```text
AdminUser                  Domain Model
   │ UserPersistenceMapper.toEntity(...)
   ▼
UserJpaEntity              Output Adapter의 DB 모델

UserJpaEntity
   │ UserPersistenceMapper.toDomain(...)
   ▼
AdminUser
```

### HTTP Request

`LoginRequest`는 JSON 필드와 HTTP 입력 검증을 표현한다.

```java
public record LoginRequest(
        @NotBlank @Size(min = 4, max = 100) String loginId,
        @NotBlank String password,
        @NotBlank @Size(max = 100) String loginReason
) {
    public LoginCommand toCommand(String clientIp, String userAgent) {
        return LoginCommand.of(
                loginId,
                password,
                loginReason,
                clientIp,
                userAgent
        );
    }
}
```

`clientIp`와 `userAgent`는 클라이언트가 JSON으로 임의 입력하게 하지 않고 서버가 HTTP 요청에서 수집하여 Command에 추가한다.

### Application Command

`LoginCommand`에는 HTTP Annotation이 없다. 로그인 유스케이스에 필요한 값만 표현한다.

```java
public record LoginCommand(
        String loginId,
        String password,
        String loginReason,
        String clientIp,
        String userAgent
) {
    public static LoginCommand of(
            String loginId,
            String password,
            String loginReason,
            String clientIp,
            String userAgent
    ) {
        return new LoginCommand(
                loginId,
                password,
                loginReason,
                clientIp,
                userAgent
        );
    }
}
```

### Application Result와 HTTP Response

`LoginResult`에는 HTTP Adapter가 HttpOnly 쿠키로 전달해야 하는 Refresh Token이 포함된다. 그러나 `LoginResponse`는 Refresh Token을 JSON으로 노출하지 않는다.

```java
public static LoginResponse from(LoginResult result) {
    return new LoginResponse(
            result.accessToken(),
            result.tokenType(),
            result.expiresInSeconds(),
            result.userId(),
            result.userName(),
            result.roleId(),
            result.roleName()
    );
}
```

계층별 DTO를 분리했기 때문에 Application 결과에 필요한 값과 외부 API에 공개할 값을 다르게 구성할 수 있다.

### 개발 규칙

| 타입 | 위치 | 역할 |
|---|---|---|
| `*Request` | `adapter.in.web.{업무}.request` | HTTP JSON과 Bean Validation |
| `*Command` | `application.dto.{업무}` | 상태 변경 유스케이스 입력 |
| `*Query` | `application.dto.{업무}` | 조회·검색·페이징 입력 |
| `*Result` | `application.dto.{업무}` | Application 실행 결과 |
| `*Response` | `adapter.in.web.{업무}.response` | 외부에 공개할 HTTP 응답 |
| `*JpaEntity` | `adapter.out.persistence.{업무}.entity` | DB 테이블과 컬럼 표현 |
| `*RedisEntity` | `adapter.out.redis.entity` | Redis Hash와 TTL 표현 |

- Request에 Domain 행위를 넣지 않는다.
- Command와 Query에 Spring MVC Annotation을 넣지 않는다.
- Domain Model에 Jackson, Validation, JPA Annotation을 넣지 않는다.
- JPA Entity를 Controller 응답으로 반환하지 않는다.
- Application Result를 검토 없이 그대로 HTTP 응답으로 반환하지 않는다.
- 각 경계에서 필요한 필드만 다음 계층으로 변환한다.

### 이 규칙의 근거

Robert C. Martin의 **『Clean Architecture』 22장 「The Clean Architecture」의 Crossing Boundaries 설명**에서는 데이터베이스의 Row나 외부 프레임워크의 데이터 형식을 안쪽 계층으로 넘기지 않고 경계를 통과하기 위한 단순 데이터 구조로 변환해야 한다고 설명한다. 이 내용 때문에 `UserJpaEntity`를 Domain과 Controller에서 함께 사용하지 않는다. [공식 장 발췌](https://www.informit.com/articles/article.aspx?p=2832399)

Martin Fowler의 **『Patterns of Enterprise Application Architecture』의 Data Transfer Object 패턴**은 호출 사이에 전달할 데이터를 하나의 객체로 묶고, 별도의 Assembler가 Domain과 DTO 사이를 변환한다고 설명한다. 현재 코드에서는 Request의 `toCommand`, Response의 `from`, Persistence Mapper가 그 변환 책임을 나누어 가진다. [Martin Fowler의 DTO 패턴](https://martinfowler.com/eaaCatalog/dataTransferObject.html)

Martin Fowler의 같은 책에 나오는 **Data Mapper 패턴**은 Domain 객체와 데이터베이스가 서로 독립적으로 유지되도록 두 표현 사이의 데이터를 옮기는 계층이다. 이 내용 때문에 `AdminUser`와 `UserJpaEntity`를 분리하고 `UserPersistenceMapper`가 변환한다. [Martin Fowler의 Data Mapper 패턴](https://martinfowler.com/eaaCatalog/dataMapper.html)

## 5. `of`, `from`, `toX` 변환 규칙

### `of(...)`

명시적으로 전달된 여러 값을 현재 타입으로 묶을 때 사용한다.

```java
LoginCommand.of(
        loginId,
        password,
        loginReason,
        clientIp,
        userAgent
);
```

```java
CreatePreAuthStateCommand.of(
        token.jti(),
        user.getId(),
        PreAuthPurpose.OTP_LOGIN,
        token.expiresInSeconds()
);
```

```java
MenuResultSource.of(menu, assigned, canView, canEdit);
```

### `from(source)`

다른 객체 하나를 현재 타입으로 변환할 때 사용한다.

```java
LoginResponse.from(loginResult);
MenuResult.from(menuResultSource);
UserStatus.from(entity.getStatus());
```

실제 `MenuResult`는 `MenuResultSource` 하나를 받아 결과로 변환한다.

```java
public static MenuResult from(MenuResultSource source) {
    return new MenuResult(
            source.menu().menuCode(),
            source.menu().name(),
            source.menu().path(),
            source.menu().parentMenuCode(),
            source.menu().sortOrder(),
            source.assigned(),
            source.canView(),
            source.canEdit()
    );
}
```

### `toX(...)`

현재 객체 또는 전용 Mapper가 다른 타입으로 변환할 때 사용한다.

```java
request.toCommand(clientIp, userAgent);
mapper.toEntity(adminUser);
mapper.toDomain(userJpaEntity);
```

### 개발 규칙

- 여러 개의 명시적 값을 조립하면 `of`를 사용한다.
- 다른 원본 객체 하나에서 변환하면 `from`을 사용한다.
- 현재 객체가 변환의 출발점이면 `toCommand`, `toQuery`처럼 목적 타입을 붙인다.
- Persistence Mapper는 `toDomain`, `toEntity`로 변환 방향을 드러낸다.
- `Command`, `Query`, `Source` record는 외부에서 `new`로 생성하지 않고 `of`를 사용한다.
- `from`과 `toX`를 동시에 만들어 같은 변환 책임을 중복하지 않는다.

### 이 규칙의 근거

Joshua Bloch의 **『Effective Java』 Item 1 「Consider static factory methods instead of constructors」는** 생성자 대신 이름을 가질 수 있는 정적 팩토리 메서드를 고려하라고 설명한다. 생성자 `new LoginCommand(...)`는 생성 의도만 알 수 있지만 `LoginCommand.of(...)`는 프로젝트가 정한 공식 생성 경로라는 사실을 보여 주고, 이후 검증이나 정규화를 팩토리 안에 추가할 수 있다. [공식 도서 페이지와 목차](https://www.informit.com/store/effective-java-9780134686097)

`of`와 `from`의 정확한 구분은 DDD 규칙이 아니라 Java 표준 라이브러리가 널리 사용한 명명 관례를 이 프로젝트에 적용한 것이다. Oracle의 **`java.time.LocalDate` 공식 API**를 보면 `LocalDate.of(year, month, day)`는 명시적 구성 값으로 객체를 만들고, `LocalDate.from(temporal)`은 다른 시간 표현에서 `LocalDate`로 변환한다. [Oracle LocalDate API](https://docs.oracle.com/javase/8/docs/api/java/time/LocalDate.html)

## 6. Command, Query, Source 파라미터 규칙

DTO는 값의 개수가 많다는 이유만으로 만들지 않는다. 여러 값이 하나의 업무 요청으로 함께 이동할 때 사용한다.

### 직접 파라미터를 사용하는 경우

한두 개 값의 역할이 메서드 이름과 타입만으로 명확하면 직접 전달한다.

```java
passwordHashPort.matches(rawPassword, encodedPassword);
userLookupPort.findById(userId);
userPersistencePort.countByRoleId(roleId);
```

```java
// 만들지 않는다.
PasswordMatchCommand.of(rawPassword, encodedPassword);
FindUserQuery.of(userId);
```

### Parameter Object를 사용하는 경우

여러 값이 항상 함께 이동하며 하나의 업무 요청을 구성하면 묶는다.

```java
public record ConsumePreAuthStateCommand(
        String jti,
        String userId,
        PreAuthPurpose purpose
) {
    public static ConsumePreAuthStateCommand of(
            String jti,
            String userId,
            PreAuthPurpose purpose
    ) {
        return new ConsumePreAuthStateCommand(jti, userId, purpose);
    }
}
```

### 접미사 규칙

| 접미사 | 사용 시점 |
|---|---|
| `*Command` | 생성, 변경, 인증, 발급처럼 작업을 수행하는 입력 |
| `*Query` | 검색 조건과 페이징처럼 조회를 수행하는 입력 |
| `*Source` | 여러 원본 값을 Result로 변환하기 위해 잠시 묶는 입력 |
| `*Result` | Application Service가 반환하는 결과 |
| `*State` | 사전 인증처럼 특정 처리 단계의 현재 상태 |

### 개발 규칙

- 현재 `Command`, `Query`, `Source` Parameter Object는 세 개 이상의 관련 값을 묶을 때 사용한다.
- 두 개 이하의 값이면 먼저 직접 파라미터로 충분한지 확인한다.
- 이름만으로 책임을 알 수 없는 `*Data`, `*Info`를 만들지 않는다.
- DTO를 다시 같은 값의 다른 DTO에 담기만 하는 중계 타입을 만들지 않는다.

세 개 이상 규칙은 DDD 원전의 규칙이 아니라 작은 DTO가 무분별하게 증가하는 것을 막기 위한 이 프로젝트의 개발 규칙이다. `MethodParameterConventionTest`가 이를 검사한다.

## 7. Aggregate Root 구현 규칙

현재 Aggregate Root는 다음 네 타입이다.

```text
AdminUser
AdminRole
LoginHistory
FileHistory
```

모두 `record`가 아니라 `final class`로 구현한다.

```java
@Getter
public final class AdminUser {
    private final String id;
    private final String loginId;
    private final String name;
    private final String email;
    private final String phoneNo;
    private final String deptName;
    private final String roleId;
    private final String passwordHash;
    private final String otpSecret;
    private final LocalDateTime lastLoginAt;
    private final UserStatus status;
    private final LocalDateTime createdAt;
    private final LocalDateTime updatedAt;

    private AdminUser(...) {
        // 모든 생성 경로가 이 생성자로 모인다.
    }
}
```

### 개발 규칙

- Aggregate Root는 `final class`로 작성한다.
- 생성자는 `private`으로 제한한다.
- 필드는 `private final`로 선언하고 Lombok `@Getter`로 읽기만 허용한다.
- Setter를 만들지 않는다.
- 식별자가 있는 Aggregate의 동등성은 식별자를 기준으로 구현한다.
- 신규 생성, DB 복원, 상태 변경은 이름이 있는 메서드로만 수행한다.
- 모든 필드에는 업무 의미가 드러나는 Javadoc을 작성한다.
- 생성자와 공개 메서드의 모든 파라미터에는 `@param` 설명을 작성한다.
- 설명에는 필요한 경우 `null` 허용 시점, 시간·크기 단위, 보안상 의미를 포함한다.

```java
/** 비밀번호 검증에 사용하는 BCrypt 해시이며 원문 비밀번호를 저장하지 않는다. */
private final String passwordHash;

/** TOTP 비밀키이며 OTP 등록 전에는 {@code null}이다. */
private final String otpSecret;

/** 비밀번호와 OTP 인증을 모두 완료한 마지막 로그인 시각이다. */
private final LocalDateTime lastLoginAt;
```

### 왜 Aggregate는 `record`로 통일하지 않는가?

Java record는 값 전체를 기준으로 `equals`와 `hashCode`를 자동 생성하고 모든 구성 요소를 공개한다. 반면 `AdminUser`는 필드 전체가 같아서 같은 사용자가 되는 것이 아니라 `id`가 같아서 같은 사용자다. 또한 신규 생성, DB 복원, 비밀번호 변경, OTP 등록처럼 수명 주기별 진입점을 통제해야 한다.

```java
AdminUser.create(...);
AdminUser.reconstitute(...);
user.update(...);
user.changePassword(...);
user.updateOtpSecret(...);
user.updateLastLoginAt(...);
```

따라서 이 프로젝트는 정체성과 수명 주기를 가진 Aggregate Root를 `final class`로 통일한다.

### 이 규칙의 근거

Eric Evans의 **『Domain-Driven Design』 5장 「Entities」는** Entity가 속성 전체가 아니라 연속되는 식별성으로 정의된다고 설명한다. `AdminUser`의 동등성을 모든 필드가 아닌 `id`로 판단하는 근거다. 같은 책 **6장 「The Life Cycle of a Domain Object」의 Aggregates 패턴**은 외부 변경이 Aggregate Root를 통해 이뤄져야 한다고 설명한다. 생성자를 private으로 제한하고 명명된 행위만 공개하는 이유다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Joshua Bloch의 **『Effective Java』 Item 15 「Minimize the accessibility of classes and members」는** 구현 상세의 접근성을 최소화하라고 설명한다. 같은 책 **Item 17 「Minimize mutability」는** 변경 가능한 상태를 최소화하고 필요한 상태를 생성 시점에 확립하라고 설명한다. private 생성자, final 필드, Setter 금지와 새 상태를 반환하는 변경 메서드에 적용한 근거다. [공식 도서 페이지와 목차](https://www.informit.com/store/effective-java-9780134686097)

Aggregate Root를 반드시 Java class로 만들어야 한다는 내용이 DDD 원전에 있는 것은 아니다. `final class` 통일은 위의 식별성·캡슐화·생성 경로 통제를 Java에서 분명하게 구현하기 위한 프로젝트 규칙이다.

## 8. record 사용 규칙

record는 값 전달 타입과 값 중심 Domain 타입에 사용한다.

### DTO record

```java
public record LoginCommand(
        String loginId,
        String password,
        String loginReason,
        String clientIp,
        String userAgent
) {
}
```

Command는 한 번 생성된 후 값이 바뀌지 않는 유스케이스 입력이므로 record가 적합하다.

### 값 중심 Domain record

```java
public record RoleMenuPermission(
        String roleId,
        String menuCode,
        boolean canView,
        boolean canEdit
) {
    public RoleMenuPermission {
        if (canEdit && !canView) {
            throw new IllegalArgumentException(
                    "편집 권한은 조회 권한과 함께 설정해야 합니다."
            );
        }
    }

    public boolean allows(MenuPermissionAction action) {
        return canView
                && (action == MenuPermissionAction.VIEW || canEdit);
    }
}
```

`RoleMenuPermission`은 생성 이후 값을 변경하지 않고, 구성된 값과 불변 조건이 중요하므로 record로 표현한다.

### 개발 규칙

- Request, Response, Command, Query, Result처럼 불변 데이터 전달 타입은 record를 우선 검토한다.
- 값의 조합으로 의미가 결정되는 Domain 타입은 record를 사용할 수 있다.
- 식별자 기반 동등성, 수명 주기, 여러 생성·변경 행위를 통제해야 하는 Aggregate Root는 record로 만들지 않는다.
- record라도 compact constructor에서 불변 조건을 검증할 수 있다.

### 이 규칙의 근거

Eric Evans의 **『Domain-Driven Design』 5장 「Value Objects」는** 식별성이 아니라 속성으로 설명되는 객체는 Value Object로 모델링하고 불변으로 다루라고 설명한다. `RoleMenuPermission`처럼 값과 규칙이 중심인 타입을 불변 record로 표현하는 근거다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Java record 사용 자체는 DDD의 요구 사항이 아니다. Java의 불변 데이터 표현 문법을 Entity와 Value Object의 차이에 맞추어 선택한 프로젝트 구현 규칙이다.

## 9. Aggregate 생성·복원·변경 규칙

### 신규 생성은 `create`

```java
public static AdminUser create(
        String loginId,
        String name,
        String email,
        String phoneNo,
        String deptName,
        String roleId,
        String passwordHash,
        UserStatus status
) {
    LocalDateTime now = LocalDateTime.now();
    return new AdminUser(
            null,
            loginId,
            name,
            email,
            phoneNo,
            deptName,
            roleId,
            passwordHash,
            null,
            null,
            status == null ? UserStatus.ACTIVE : status,
            now,
            now
    );
}
```

신규 사용자는 아직 ID가 없고 OTP Secret과 마지막 로그인 시각도 없다. `create`가 이 초기 상태를 결정한다.

### DB 상태 복원은 `reconstitute`

```java
public static AdminUser reconstitute(
        String id,
        String loginId,
        String name,
        String email,
        String phoneNo,
        String deptName,
        String roleId,
        String passwordHash,
        String otpSecret,
        LocalDateTime lastLoginAt,
        UserStatus status,
        LocalDateTime createdAt,
        LocalDateTime updatedAt
) {
    return new AdminUser(
            id,
            loginId,
            name,
            email,
            phoneNo,
            deptName,
            roleId,
            passwordHash,
            otpSecret,
            lastLoginAt,
            status,
            createdAt,
            updatedAt
    );
}
```

DB에서 조회한 사용자를 `create`로 만들면 ID, OTP Secret, 생성 시각이 신규 기본값으로 바뀔 수 있다. 그래서 기존 상태 복원은 별도 메서드로 구분한다.

### 변경은 업무 이름을 사용

```java
user.update(...);
user.changePassword(encodedPassword);
user.updateOtpSecret(secret);
user.updateLastLoginAt(LocalDateTime.now());
```

로그인 이력도 범용 `create`를 외부에 공개하지 않고 어떤 인증 사건인지 이름으로 표현한다.

```java
LoginHistory.loginSucceeded(...);
LoginHistory.loginFailed(...);
LoginHistory.otpSucceeded(...);
LoginHistory.otpFailed(...);
```

```java
loginHistoryPersistencePort.save(
        LoginHistory.otpFailed(
                user.getId(),
                loginReason,
                failReason,
                user.getLoginId(),
                command.clientIp(),
                command.userAgent()
        )
);
```

### `*CreateData`, `*UpdateData`를 만들지 않는다

```java
// 금지
AdminUser.create(AdminUserCreateData.of(...));
adminUser.update(AdminUserUpdateData.of(...));
LoginHistory.create(LoginHistoryCreateData.of(...));
```

이 객체들은 Domain 개념이나 규칙 없이 필드를 한 번 더 운반한다. 호출 흐름만 늘어나고 Aggregate의 생성·변경 API가 무엇을 의미하는지 가린다.

여러 필드가 독립적인 업무 개념과 불변 조건을 가진다면 `*Data` 대신 실제 Value Object로 추출한다.

### 이 규칙의 근거

Eric Evans의 **『Domain-Driven Design』 6장 「Factories」는** 복잡한 Domain 객체의 생성 책임을 캡슐화하고, 생성 완료 시 객체가 유효한 상태가 되도록 해야 한다고 설명한다. `AdminUser.create`, `LoginHistory.otpFailed`처럼 생성 의미와 초기 규칙을 Aggregate 내부에 둔 근거다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Vaughn Vernon의 **『Implementing Domain-Driven Design』 11장 「Factories」는** Factory가 단순히 생성자 파라미터를 감추는 것이 아니라 올바른 Domain 객체를 만드는 책임을 가져야 한다고 설명한다. 아무 규칙 없는 `*CreateData`를 추가하지 않고 목적이 드러나는 Factory 메서드를 사용한 이유다. [공식 도서 페이지](https://www.informit.com/store/implementing-domain-driven-design-9780133039894)

`reconstitute`라는 이름은 DDD가 강제하는 메서드명이 아니라 신규 생성과 영속 상태 복원을 혼동하지 않기 위해 정한 프로젝트 규칙이다.

## 10. Aggregate 참조 규칙

`AdminUser`는 `AdminRole` 객체 전체를 보유하지 않고 `roleId`만 보유한다.

```java
public final class AdminUser {
    private final String id;
    private final String roleId;
    // ...
}
```

로그인 시 사용자와 권한이 모두 필요하면 Application Service가 각각 조회한다.

```java
AdminUser user = userLookupPort.findByLoginId(command.loginId())
        .orElseThrow(this::invalidCredentials);

user.validateLoginAllowed();

AdminRole role = rolePersistencePort.findById(user.getRoleId())
        .orElseThrow(...);

role.validateLoginAllowed();
```

### 개발 규칙

- 다른 Aggregate Root를 필드로 직접 포함하지 않고 ID로 참조한다.
- 두 Aggregate가 필요한 유스케이스는 Application Service가 각각 Repository Port로 조회한다.
- 한 Aggregate의 변경 때문에 다른 Aggregate 전체를 함께 저장하지 않는다.
- 즉시 일관성이 반드시 필요한 진짜 업무 불변 조건만 같은 Aggregate 경계에 둔다.

### 이 규칙의 근거

Vaughn Vernon의 **『Implementing Domain-Driven Design』 10장 「Aggregates」에서** 제시하는 실전 규칙은 “작은 Aggregate를 설계하고 다른 Aggregate는 식별자로 참조하라”는 것이다. Aggregate 객체 그래프를 직접 연결하면 하나를 조회·변경할 때 경계 밖 데이터까지 함께 로딩하고 하나의 트랜잭션으로 묶기 쉽기 때문이다. `AdminUser.roleId`가 이 규칙을 적용한 코드다. [Vaughn Vernon의 Aggregate 장 공식 발췌](https://www.informit.com/articles/article.aspx?p=2020371)

## 11. Application Service 규칙

Application Service는 유스케이스의 실행 순서를 조정한다. Aggregate 자신의 상태만으로 판단할 수 있는 규칙은 Aggregate가 처리하고, 여러 Aggregate와 외부 기술을 함께 사용해야 하는 순서는 Application Service가 처리한다.

### `LoginService`에 적용한 구분

```java
@Override
@Transactional
public LoginChallengeResult login(LoginCommand command) {
    AdminUser user = userLookupPort.findByLoginId(command.loginId())
            .orElseThrow(this::invalidCredentials);

    validateLoginAllowed(user);

    if (!passwordHashPort.matches(
            command.password(),
            user.getPasswordHash()
    )) {
        throw invalidCredentials();
    }

    IssuedPreAuthToken token = preAuthTokenPort.issue(
            user.getId(),
            PreAuthPurpose.OTP_LOGIN
    );

    preAuthStatePort.create(CreatePreAuthStateCommand.of(...));
    loginHistoryPersistencePort.save(LoginHistory.loginSucceeded(...));

    return new LoginChallengeResult(...);
}
```

| 처리 | 위치 | 이유 |
|---|---|---|
| 사용자가 활성 상태인가? | `AdminUser.validateLoginAllowed()` | 사용자 자신의 상태로 판단 가능 |
| 권한이 활성 상태인가? | `AdminRole.validateLoginAllowed()` | 권한 자신의 상태로 판단 가능 |
| 사용자와 권한을 어떤 순서로 조회하는가? | `LoginService` | 두 Aggregate를 조합하는 유스케이스 흐름 |
| 비밀번호를 BCrypt로 비교하는가? | `PasswordHashPort` 구현 Adapter | 외부 암호화 기술 |
| 사전 인증 토큰을 언제 발급하는가? | `LoginService` | 로그인 처리 순서 |
| Redis에 어떻게 저장하는가? | `PreAuthStatePort` 구현 Adapter | 외부 저장 기술 |

### 개발 규칙

- 모든 Application Service는 `@Service`로 Component Scan 대상이 된다.
- 별도 `ApplicationServiceConfig`에서 Service를 수동으로 Bean 등록하지 않는다.
- Application Service는 Input Port를 구현한다.
- Application Service는 Domain과 Output Port를 조합한다.
- 한 Aggregate 자신의 상태로 판단 가능한 업무 규칙은 Aggregate 메서드로 옮긴다.
- JPA, Redis, JWT, BCrypt 구현 코드를 Service에 작성하지 않는다.
- Service가 다른 Application Service나 다른 Input Port를 주입받지 않는다.

### Service가 Service를 호출하지 않는다

다음 구조는 인터페이스를 거쳤더라도 결국 Application Service 간 호출이다.

```java
// 금지
public class TokenSessionService {
    private final MenuQueryUseCase menuQueryUseCase;
}
```

현재 `MenuService`는 필요한 Output Port를 직접 조합한다.

```java
@Service
@RequiredArgsConstructor
public class MenuService implements MenuQueryUseCase {
    private final UserLookupPort userLookupPort;
    private final RolePersistencePort rolePersistencePort;
    private final MenuCatalogPort menuCatalogPort;
    private final RoleMenuPersistencePort roleMenuPersistencePort;
}
```

공통 로직이 생기면 다음 기준으로 이동한다.

- 특정 Aggregate의 상태 규칙: 해당 Aggregate
- 여러 Domain 값으로 판단하지만 외부 기술이 필요 없는 정책: Domain Service 검토
- 비밀번호, 토큰, Redis, Excel 같은 기술 기능: Output Port
- 유스케이스마다 달라지는 실행 순서: 각 Application Service

### 이 규칙의 근거

Martin Fowler의 **『Patterns of Enterprise Application Architecture』의 Service Layer 패턴**은 Service Layer를 애플리케이션 경계로 정의하고, 클라이언트가 사용할 수 있는 작업과 각 작업에 대한 응답의 조정을 담당한다고 설명한다. 즉 Service Layer의 역할은 로그인·사용자 생성 같은 작업의 시작과 끝, 트랜잭션, 여러 협력 객체의 호출 순서를 관리하는 것이다. [Martin Fowler의 Service Layer 패턴](https://martinfowler.com/eaaCatalog/serviceLayer.html)

Eric Evans의 **『Domain-Driven Design』 5장 「Services」는** 중요한 업무 과정이 Entity나 Value Object 한 곳의 책임이 아닐 때 상태 없는 Domain Service로 표현할 수 있다고 설명한다. 반대로 사용자 활성 여부처럼 한 Aggregate가 자신의 상태로 판단할 수 있는 규칙까지 Application Service에 둘 이유는 없다. 이 구분 때문에 `AdminUser.validateLoginAllowed()`는 Domain에 있고 사용자·권한·토큰·Redis 호출 순서는 `LoginService`에 있다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Service 간 호출 금지는 위 책의 절대 규칙이 아니라 유스케이스 호출 사슬, 순환 의존, 불분명한 트랜잭션 경계를 막기 위한 프로젝트 규칙이다. `MethodParameterConventionTest`가 Application Service의 Input Port 의존을 검사한다.

## 12. Input Port와 Output Port 규칙

### Input Port

Input Port는 외부에서 실행할 수 있는 유스케이스 계약이다.

```java
public interface LoginUseCase {
    LoginChallengeResult login(LoginCommand command);
}
```

```java
public class LoginService implements LoginUseCase {
    // ...
}
```

```java
public class AuthController {
    private final LoginUseCase loginUseCase;
}
```

Controller는 구체적인 `LoginService` 대신 `LoginUseCase`를 호출한다.

### Output Port

Output Port는 Application이 외부 기술에 요구하는 기능이다.

```java
public interface UserPersistencePort {
    AdminUser save(AdminUser user);
    long countByRoleId(String roleId);
}
```

```java
public interface PasswordHashPort {
    String encode(String rawPassword);
    boolean matches(String rawPassword, String encodedPassword);
}
```

Application이 필요한 언어로 Port를 정의하고 JPA, BCrypt 같은 Adapter가 구현한다.

### 개발 규칙

- Input Port는 하나의 유스케이스를 나타낸다.
- Output Port는 Application이 필요로 하는 외부 기능을 나타낸다.
- Output Port 인터페이스는 `application.port.out`에 둔다.
- 기술 라이브러리의 타입을 Port 메서드에 노출하지 않는다.
- Port 이름과 메서드는 기술 명령이 아니라 Application의 요구를 표현한다.
- private 메서드를 감추기 위해 인터페이스를 만들지 않는다.
- Service 간 호출을 감추기 위해 Input Port를 주입하지 않는다.
- DTO를 한 번 더 옮겨 담기만 하는 중계 Port를 만들지 않는다.

### 이 규칙의 근거

Alistair Cockburn의 **「Hexagonal Architecture」에서** Port는 애플리케이션과 외부 세계가 상호작용하는 목적별 통로이고, Adapter는 특정 기술을 그 Port에 맞추는 변환기다. 따라서 `UserPersistencePort`는 Application에 있고 `UserPersistenceAdapter`가 JPA 기술로 이를 구현한다. [Alistair Cockburn의 원문](https://alistair.cockburn.us/hexagonal-architecture)

Port가 많을수록 Hexagonal Architecture에 가깝다는 뜻은 아니다. 외부 경계가 아닌 내부 메서드마다 인터페이스를 만들면 Cockburn이 말한 Port의 목적과 다르다.

## 13. Persistence Port와 Repository 규칙

Aggregate 저장 Port는 중간 Command가 아니라 Aggregate Root를 직접 받는다.

```java
public interface UserPersistencePort {
    AdminUser save(AdminUser user);
}
```

```java
public interface RolePersistencePort {
    AdminRole save(AdminRole role);
}
```

```java
public interface LoginHistoryPersistencePort {
    LoginHistory save(LoginHistory history);
}
```

```java
public interface FileHistoryPersistencePort {
    FileHistory save(FileHistory history);
}
```

### 중계 Command를 사용하지 않는다

```java
// 금지
recordLoginHistory(RecordLoginHistoryCommand.of(...));

private void recordLoginHistory(RecordLoginHistoryCommand command) {
    loginHistoryPersistencePort.save(
            LoginHistory.create(...)
    );
}
```

```java
// 현재 방식
loginHistoryPersistencePort.save(
        LoginHistory.loginSucceeded(
                user.getId(),
                command.loginReason(),
                command.loginId(),
                command.clientIp(),
                command.userAgent()
        )
);
```

Application Service가 이미 필요한 값을 가지고 있고 Domain Factory를 호출할 수 있으므로 Aggregate를 만든 뒤 바로 Persistence Port에 전달한다.

### 이 규칙의 근거

Eric Evans의 **『Domain-Driven Design』 6장 「Repositories」는** Aggregate를 조회하고 저장하는 진입점을 Repository로 제공하며, 클라이언트가 영속성 상세를 알지 않도록 해야 한다고 설명한다. Repository의 대상이 Aggregate이므로 저장 Port가 `AdminUser`, `AdminRole`을 직접 받는다. [Eric Evans의 DDD Reference](https://www.domainlanguage.com/ddd/reference/)

Vaughn Vernon의 **『Implementing Domain-Driven Design』 12장 「Repositories」**와 저자 인터뷰에서는 Repository가 완전한 Aggregate를 저장·조회하고 Aggregate는 영속성이 아니라 업무 행위와 일관성에 집중해야 한다고 설명한다. `RecordLoginHistoryCommand` 같은 저장 전용 중계 객체를 만들지 않는 근거다. [Vaughn Vernon의 Aggregate와 Repository 인터뷰](https://www.informit.com/articles/article.aspx?p=2023702)

Martin Fowler의 **Repository 패턴**은 Domain과 Data Mapper 사이에서 객체 컬렉션과 유사한 인터페이스를 제공한다고 설명한다. JPA Repository 자체를 Application에 노출하지 않고 Persistence Adapter 뒤에 두는 이유다. [Martin Fowler의 Repository 패턴](https://martinfowler.com/eaaCatalog/repository.html)

## 14. JPA Entity와 Persistence Mapper 규칙

`AdminUser`는 Domain Model이고 `UserJpaEntity`는 DB 저장 모델이다. 두 객체를 Mapper가 변환한다.

```java
@Component
public class UserPersistenceMapper {

    public UserJpaEntity toEntity(AdminUser user) {
        return new UserJpaEntity(
                id(user.getId()),
                user.getLoginId(),
                user.getName(),
                user.getEmail(),
                user.getPhoneNo(),
                user.getDeptName(),
                id(user.getRoleId()),
                user.getPasswordHash(),
                user.getStatus().toYn(),
                user.getOtpSecret(),
                user.getLastLoginAt(),
                user.getCreatedAt(),
                user.getUpdatedAt()
        );
    }

    public AdminUser toDomain(UserJpaEntity entity) {
        return AdminUser.reconstitute(
                String.valueOf(entity.getId()),
                entity.getLoginId(),
                entity.getName(),
                entity.getEmail(),
                entity.getPhoneNo(),
                entity.getDeptName(),
                String.valueOf(entity.getRoleId()),
                entity.getPasswordHash(),
                entity.getOtpSecret(),
                entity.getLastLoginAt(),
                UserStatus.from(entity.getStatus()),
                entity.getCreatedAt(),
                entity.getUpdatedAt()
        );
    }
}
```

Mapper는 다음 차이를 처리한다.

- DB의 `Long` ID와 Domain의 `String` ID
- DB의 Y/N 상태와 `UserStatus`
- JPA Entity의 저장 형식과 Domain 타입
- 신규 생성이 아닌 기존 영속 상태의 `reconstitute`

### 개발 규칙

- JPA Annotation은 `*JpaEntity`에만 둔다.
- Domain Model에 `@Entity`, `@Table`, `@Column`을 붙이지 않는다.
- Persistence Adapter는 Mapper를 통해 Domain과 Entity를 변환한다.
- `toDomain`은 기존 DB 상태를 복원하므로 Aggregate의 `reconstitute`를 사용한다.
- DB의 ID와 상태 표현 차이는 Mapper에서 처리한다.
- JPA Entity를 Application Service와 Controller로 반환하지 않는다.

### 이 규칙의 근거

Martin Fowler의 **『Patterns of Enterprise Application Architecture』의 Data Mapper 패턴**은 메모리 객체와 데이터베이스 사이에서 데이터를 이동하면서 두 표현을 서로 독립적으로 유지하는 Mapper 계층을 설명한다. `UserPersistenceMapper`가 정확히 이 역할을 수행한다. [Martin Fowler의 Data Mapper 패턴](https://martinfowler.com/eaaCatalog/dataMapper.html)

Robert C. Martin의 **『Clean Architecture』 22장**에서도 Database는 외부 세부 사항이므로 Database Row를 안쪽 업무 계층으로 넘기지 않아야 한다고 설명한다. Domain에 JPA Annotation을 넣지 않는 근거다. [공식 장 발췌](https://www.informit.com/articles/article.aspx?p=2832399)

## 15. Redis Adapter와 Repository Fragment 규칙

Redis의 기본 저장·조회는 Spring Data Redis Repository를 사용한다.

```java
@RedisHash(PreAuthStateRedisEntity.KEYSPACE)
public class PreAuthStateRedisEntity {
    public static final String KEYSPACE = "admin-core:pre-auth";

    @Id
    private final String jti;

    private final String userId;
    private final String purpose;
    private final int failedAttempts;

    @TimeToLive(unit = TimeUnit.SECONDS)
    private final long ttlSeconds;
}
```

```java
public interface PreAuthStateRedisRepository
        extends ListCrudRepository<PreAuthStateRedisEntity, String>,
                PreAuthStateRedisAtomicOperations {
}
```

### 기본 CRUD

다음 작업은 `ListCrudRepository`를 사용한다.

- 사전 인증 상태 저장
- ID로 사전 인증 상태 조회
- Refresh Token 상태 저장·조회·삭제
- TTL이 있는 Redis Hash 객체 관리

### 복합 원자 연산

다음 작업은 Repository Fragment와 Lua Script를 사용한다.

- 저장된 사용자와 목적이 일치할 때만 사전 인증 상태 삭제
- OTP 실패 횟수 증가와 최대 횟수 도달 시 삭제
- 현재 Refresh Token 해시가 일치할 때만 새 해시로 교체
- 토큰 해시가 일치할 때만 Refresh 상태 삭제

```java
public interface PreAuthStateRedisAtomicOperations {
    int incrementFailureAndDeleteAtLimit(String jti, int maxAttempts);
    boolean consumeIfMatches(String jti, String userId, String purpose);
}
```

```java
public class PreAuthStateRedisAtomicOperationsImpl
        implements PreAuthStateRedisAtomicOperations {

    private static final RedisScript<Long> CONSUME =
            new DefaultRedisScript<>("""
                    local userId = redis.call('HGET', KEYS[1], 'userId')
                    local purpose = redis.call('HGET', KEYS[1], 'purpose')

                    if not userId
                       or userId ~= ARGV[1]
                       or purpose ~= ARGV[2] then
                        return 0
                    end

                    redis.call('DEL', KEYS[1])
                    return 1
                    """, Long.class);

    private final StringRedisTemplate redisTemplate;
}
```

조회와 삭제를 Java의 별도 호출로 실행하면 두 호출 사이에 다른 요청이 같은 상태를 사용할 수 있다. Script는 검증과 삭제를 Redis 서버에서 하나의 작업으로 실행한다.

### 개발 규칙

- Redis 객체 구조, ID, TTL은 `*RedisEntity`로 표현한다.
- 단순 CRUD는 `ListCrudRepository`를 사용한다.
- 조건 확인과 변경이 분리되면 경쟁 조건이 생기는 작업만 Lua Script를 사용한다.
- Lua 구현은 `adapter.out.redis.repository`의 Repository Fragment 구현체에 둔다.
- Application Service에서 `StringRedisTemplate`과 `RedisScript`를 직접 사용하지 않는다.
- 짧고 해당 Fragment에서만 사용하는 Script는 Java Text Block에 둔다.
- Script가 길어지거나 여러 구현에서 공유될 때만 별도 `.lua` 리소스 분리를 검토한다.

### 이 규칙의 근거

Spring Data Redis의 **Redis Repositories 공식 문서**는 Redis Hash 객체 매핑, Repository 기반 CRUD, TTL, 사용자 정의 Repository 구현을 설명한다. `@RedisHash`, `@TimeToLive`, `ListCrudRepository`, Repository Fragment를 함께 사용하는 근거다. [Spring Data Redis 공식 문서](https://docs.spring.io/spring-data/redis/reference/repositories.html)

Redis의 **Scripting with Lua 공식 문서**는 Script 실행 중 다른 명령이 끼어들지 않도록 원자적으로 실행된다고 설명한다. 사용자·목적 확인 후 삭제, 실패 횟수 증가 후 제한 도달 시 삭제를 Lua로 묶은 근거다. [Redis Lua Script 공식 문서](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Java Text Block에 Script를 두는 것은 공식 문서의 요구 사항이 아니라 현재처럼 짧은 Script와 구현 위치를 함께 확인하기 위한 프로젝트 규칙이다.

## 16. Controller 규칙

Controller는 HTTP 요청을 Application 호출로 연결하고 결과를 HTTP 응답으로 변환한다.

```java
@PostMapping("/otp/verify")
public ResponseEntity<ApiResponse<LoginResponse>> verifyOtp(
        @Valid @RequestBody OtpVerifyRequest request,
        @ClientIp String clientIp,
        @RequestHeader(
                value = "User-Agent",
                defaultValue = "Unknown"
        ) String userAgent
) {
    LoginResult result = otpVerifyUseCase.verifyOtp(
            request.toCommand(clientIp, userAgent)
    );

    return ApiResponse.ok(LoginResponse.from(result))
            .toResponseEntity(refreshTokenCookie.issue(result));
}
```

위 메서드는 다음 네 단계만 수행한다.

1. HTTP 입력을 받는다.
2. Request를 Command로 변환한다.
3. Input Port를 호출한다.
4. Result를 Response와 HTTP 응답으로 변환한다.

### private 응답 조립 메서드를 만들지 않는다

Controller마다 다음 메서드를 반복하지 않는다.

```java
// 금지
private ResponseEntity<byte[]> createExcelResponse(...) {
    // Header와 Content-Type 조립
}
```

HTTP 응답 변환 책임을 가진 객체의 공개 메서드를 사용한다.

```java
ApiResponse.ok(data).toResponseEntity();
ApiResponse.ok(data).toResponseEntity(responseCookie);
ApiResponse.toExcelResponseEntity(fileName, fileBytes);
```

Refresh Token 쿠키 생성과 만료는 인증 Web Adapter가 소유한다.

```text
adapter.in.web.auth.cookie.RefreshTokenCookie
```

CORS 설정은 Web 입력 Adapter의 DTO가 아니라 애플리케이션 실행 설정이므로 다음 위치에 둔다.

```text
config.CorsProperties
```

### 개발 규칙

- Controller는 Input Port만 호출한다.
- Controller에서 Output Port, JPA Repository, Redis Repository를 호출하지 않는다.
- Controller에서 Domain 상태를 판단하거나 변경하지 않는다.
- Request의 `toCommand` 또는 `toQuery`로 Application 입력을 만든다.
- Application Result는 Response의 `from`으로 HTTP 응답 형태를 결정한다.
- Controller에 private 업무 메서드와 private 응답 조립 메서드를 만들지 않는다.
- 쿠키 로직은 해당 HTTP 업무 Adapter에 둔다.
- CORS와 Security Filter Chain은 `config`에 둔다.

### 이 규칙의 근거

Alistair Cockburn의 **「Hexagonal Architecture」에서** Input Adapter는 외부 이벤트를 Application Port 호출로 변환한다. Controller가 Request를 Command로 변환하고 Input Port를 호출하는 이유다. Controller가 JPA와 Redis를 직접 호출하면 Application 경계를 건너뛰게 된다. [Alistair Cockburn의 원문](https://alistair.cockburn.us/hexagonal-architecture)

Controller의 private 메서드 금지는 DDD나 Hexagonal Architecture의 보편 규칙이 아니다. endpoint의 전체 흐름을 한눈에 보이게 하고, HTTP 응답 변환을 `ApiResponse`와 쿠키 객체에 모으기 위한 프로젝트 규칙이다.

## 17. Security Input Adapter 규칙

인증 요청도 Web Controller와 같은 입력 Adapter 원칙을 적용한다.

```text
Authorization Header
        ▼
JwtAuthenticationFilter              Security Input Adapter
        ▼
AccessTokenAuthenticationUseCase     Application Input Port
        ▼
AccessTokenAuthenticationService     Application Service
        ├─ JwtTokenPort
        ├─ UserLookupPort
        └─ RolePersistencePort
        ▼
AuthenticatedAccount                 Application 결과
        ▼
AdminPrincipal / SecurityContext     Spring Security 표현
```

### 개발 규칙

- `JwtAuthenticationFilter`는 Authorization Header 추출과 SecurityContext 설정만 담당한다.
- JWT 검증 후 현재 사용자와 권한을 확인하는 흐름은 `AccessTokenAuthenticationUseCase`에 위임한다.
- `AdminPrincipal`, `Authentication`, `SecurityContext`는 `adapter.in.security` 밖으로 전달하지 않는다.
- Domain Model에 Spring Security 인터페이스를 구현하지 않는다.
- 인증은 인가보다 먼저 실행되도록 Security Filter 순서를 구성한다.

### 이 규칙의 근거

Spring Security의 **Servlet Authentication Architecture 공식 문서**는 Servlet Filter가 Security Filter Chain에서 인증을 처리하고, 인증 결과를 `SecurityContextHolder`에 저장하는 구조를 설명한다. `JwtAuthenticationFilter`와 `AdminPrincipal`이 Domain이 아니라 Security Input Adapter에 위치하는 근거다. [Spring Security 공식 문서](https://docs.spring.io/spring-security/reference/servlet/architecture.html)

Filter가 JWT 라이브러리, 사용자 DB 조회와 권한 규칙을 모두 직접 구현하지 않는 이유는 Cockburn의 Input Adapter 역할과 같다. Filter는 Spring Security 형식을 Application Port 호출로 변환해야 한다.

## 18. 트랜잭션 규칙

트랜잭션은 Application Service 클래스 전체가 아니라 public 유스케이스 메서드에 선언한다.

```java
@Service
@RequiredArgsConstructor
public class UserService
        implements UserCommandUseCase, UserQueryUseCase {

    @Transactional
    public UserResult createUser(CreateUserCommand command) {
        // 사용자 생성
    }

    @Transactional
    public UserResult updateUser(UpdateUserCommand command) {
        // 사용자 수정
    }

    @Transactional(readOnly = true)
    public UserResult getUser(String userId) {
        // 사용자 조회
    }
}
```

### 개발 규칙

- 클래스에 `@Transactional`을 선언하지 않는다.
- DB를 변경하는 public 유스케이스 메서드에 `@Transactional`을 선언한다.
- DB를 조회하는 public 유스케이스 메서드에 `@Transactional(readOnly = true)`를 선언한다.
- private 메서드에 `@Transactional`을 선언하지 않는다.
- 같은 클래스의 메서드를 호출하면서 새로운 트랜잭션이 적용될 것이라고 기대하지 않는다.
- Redis 상태만 변경하고 JPA 작업이 없는 `TokenSessionService`에는 JPA 트랜잭션을 선언하지 않는다.

감사 이력은 본 작업의 실패와 독립적으로 기록해야 하므로 Persistence Adapter에서 새 트랜잭션을 사용한다.

```java
@Override
@Transactional(propagation = Propagation.REQUIRES_NEW)
public LoginHistory save(LoginHistory history) {
    return mapper.toDomain(
            repository.save(mapper.toEntity(history))
    );
}
```

### 이 규칙의 근거

Spring Framework의 **Using `@Transactional` 공식 문서**는 Transaction Annotation을 영향을 받는 코드 가까이에 선언할 수 있으며 구체 클래스의 메서드에 선언하는 방식을 권장한다. 현재 프로젝트는 어떤 유스케이스가 조회이고 변경인지 선언부에서 바로 확인할 수 있도록 메서드에만 작성한다. [Spring Transaction 공식 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

같은 공식 문서의 **proxy mode 설명**에서는 외부에서 Proxy를 통과한 호출만 가로채며 같은 객체 내부의 self-invocation은 실제 Transaction interception을 발생시키지 않는다고 설명한다. private 메서드에 `@Transactional`을 붙이지 않고 public 유스케이스를 트랜잭션 경계로 삼는 직접적인 근거다.

Martin Fowler의 **『Patterns of Enterprise Application Architecture』의 Unit of Work 패턴**은 하나의 업무 트랜잭션에서 변경된 객체와 DB 반영을 조정한다고 설명한다. Application Service의 유스케이스 메서드를 한 업무 단위로 잡는 설계 근거다. [Martin Fowler의 Unit of Work 패턴](https://martinfowler.com/eaaCatalog/unitOfWork.html)

메서드 단위 선언은 Spring의 필수 규칙이 아니라 클래스 단위 기본값으로 인한 의도하지 않은 트랜잭션을 막기 위한 프로젝트 규칙이다.

## 19. 주석과 이름 규칙

### 주석은 처리 이유와 업무 의미를 설명한다

```java
// 사전 인증 토큰과 Redis 인증 상태를 검증한다.
PreAuthClaims claims = validatePreAuth(command.preAuthToken());

// OTP 검증 후 사전 인증 상태를 소비해 같은 토큰의 재사용을 막는다.
validateOtp(user, claims, command, loginReason);
consumePreAuthState(claims, user.getId());
```

다음처럼 코드 문장을 그대로 반복하지 않는다.

```java
// user 변수에 사용자를 저장한다.
AdminUser user = userLookupPort.findById(userId).orElseThrow(...);
```

### 메서드 내부 주석

- 여러 단계가 있는 유스케이스는 순서를 이해할 수 있는 짧은 주석을 작성한다.
- 코드 자체로 분명한 대입과 반환에는 주석을 작성하지 않는다.
- 보안 검증 순서, 원자 연산, 실패 이력처럼 순서에 이유가 있으면 그 이유를 작성한다.
- 지나치게 긴 설명은 메서드 Javadoc으로 옮기고 내부 주석은 담백하게 유지한다.

### Aggregate Javadoc

- 모든 필드의 업무 의미를 설명한다.
- `null`이 가능한 필드는 언제 `null`인지 설명한다.
- 시간, 크기, TTL은 단위를 설명한다.
- 비밀번호 해시와 OTP Secret은 원문 여부와 보안 의미를 설명한다.
- 공개 Factory와 행위 메서드는 모든 `@param`, `@return`, 주요 `@throws`를 작성한다.

### 이름 규칙

| 대상 | 이름 예시 |
|---|---|
| 업무 행위 | `changePassword`, `validateLoginAllowed`, `otpFailed` |
| 상태 변경 입력 | `CreateUserCommand`, `UpdateRoleCommand` |
| 조회 입력 | `UserQuery`, `LoginHistoryQuery` |
| Application 결과 | `UserResult`, `MenuListResult` |
| DB 모델 | `UserJpaEntity` |
| Redis 모델 | `PreAuthStateRedisEntity` |
| 변환 | `toCommand`, `toDomain`, `toEntity`, `from` |
| 신규 Aggregate | `create` |
| 영속 상태 복원 | `reconstitute` |

`Data`, `Info`, `Manager`, `Helper`, `Util`처럼 책임 범위가 드러나지 않는 이름은 사용하지 않는다. 먼저 실제 소유 업무와 행위를 이름으로 표현한다.

## 20. 아키텍처 규칙 자동 검사

현재 개발 규칙은 다음 테스트로 보호한다.

### `CoreDependencyRuleTest`

- Application의 `adapter`, `config`, `jakarta` 의존 금지
- Application의 Spring 의존성을 `@Service`, `@Transactional`로 제한
- Domain의 Spring, Jakarta, Application, Adapter, Common, Config 의존 금지

### `AggregateRootConventionTest`

- `AdminUser`, `AdminRole`, `LoginHistory`, `FileHistory`가 `final class`인지 검사
- Aggregate Root 생성자가 private인지 검사

### `MethodParameterConventionTest`

- Domain에 `*CreateData`, `*UpdateData`가 없는지 검사
- Persistence Port가 Aggregate Root를 직접 저장하는지 검사
- Application Service가 다른 Input Port에 의존하지 않는지 검사
- Application Service에 `@Service`가 있는지 검사
- Application Service에 클래스 단위 `@Transactional`이 없는지 검사
- `Command`, `Query`, `Source`가 세 개 이상의 값을 가지는지 검사
- `Command`, `Query`, `Source`가 `of` Factory를 제공하는지 검사
- 해당 Parameter Object를 선언 파일 밖에서 `new`로 생성하지 않는지 검사

### `TransactionBoundaryDeclarationTest`

- OTP 검증과 권한 생성 등 주요 변경 유스케이스에 메서드 단위 트랜잭션이 선언됐는지 검사
- 이력을 함께 저장하는 Excel 내보내기 유스케이스가 쓰기 트랜잭션인지 검사
- `TokenSessionService`에 불필요한 클래스 단위 트랜잭션이 없는지 검사

규칙을 변경해야 한다면 테스트를 삭제해서 우회하지 않는다. 변경할 아키텍처 규칙, 실제 코드, 해당 자동 검사 내용을 함께 수정한다.
