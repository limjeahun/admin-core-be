# 인증·인가 구조

## 기본 원칙

- 서버 HTTP Session을 생성하지 않는 `STATELESS` 구조다.
- 일반 보호 API는 `Authorization: Bearer {accessToken}`으로 인증한다.
- Refresh Token은 응답 JSON이 아니라 HttpOnly 쿠키로 전달한다.
- 사용자·역할·메뉴 권한은 요청 시점의 DB 상태를 다시 조회한다.
- Spring Security 의존 코드는 입력 어댑터에 두고 인증 업무 규칙은 Application Service와 출력 Port로 처리한다.

```text
HTTP 요청
  ↓
Spring SecurityFilterChain
  ↓
JwtAuthenticationFilter
  ↓ AccessTokenAuthenticationUseCase
AccessTokenAuthenticationService
  ↓
SecurityContext
  ↓
URL 인증·메뉴 권한 검사
  ↓
Controller
```

## 로그인 1단계: ID와 비밀번호

`POST /api/v1/auth/login`은 로그인 ID, 평문 비밀번호와 접속 사유를 받는다.

1. `LoginService`가 `UserLookupPort`로 사용자를 조회한다.
2. `AdminUser`가 활성 상태를 검사한다.
3. `RolePersistencePort`로 현재 역할을 조회하고 `AdminRole`이 활성 상태를 검사한다.
4. `PasswordHashPort`가 평문 비밀번호와 BCrypt 해시를 비교한다.
5. `PreAuthTokenPort`가 OTP 단계에서 사용할 짧은 수명의 pre-auth JWT를 발급한다.
6. `PreAuthStatePort`가 토큰 ID, 사용자, 목적과 실패 횟수를 Redis에 저장한다.
7. `LoginHistory.loginSucceeded(...)` 또는 `loginFailed(...)`로 감사 이력을 저장한다.

```text
AuthController                         adapter.in.web.auth
  ↓ LoginUseCase
LoginService                           application.service.auth
  ├─ UserLookupPort
  ├─ RolePersistencePort
  ├─ PasswordHashPort
  ├─ PreAuthTokenPort
  ├─ PreAuthStatePort
  └─ LoginHistoryPersistencePort
       ↓
JPA / BCrypt / JWT / Redis             adapter.out
```

로그인 결과의 pre-auth token은 최종 Access Token이 아니다. OTP 등록 또는 검증 API의 요청 본문에만 사용한다.

## OTP 등록

OTP 비밀키가 없는 사용자는 `PUT /api/v1/auth/otp/barcode`를 호출한다.

1. 요청 본문의 pre-auth JWT를 검증한다.
2. JWT의 `jti`, 사용자 ID, 목적이 Redis 사전 인증 상태와 일치하는지 확인한다.
3. 사용자와 역할의 현재 활성 상태를 확인한다.
4. 새 TOTP Secret과 인증 앱 등록 URI, QR 이미지를 생성한다.
5. QR 안내 메일 발송이 성공한 후에만 `AdminUser.updateOtpSecret(...)` 결과를 저장한다.

QR 메일 발송에 사용하는 `JavaMailSenderImpl`은 `config.MailConfig`가 생성한다. `application.yml`은 전달받은 팀의
`SPRING_MAIL_*` 환경 변수를 `spring.mail.*`로 바인딩하고, Config는 이 설정에 SMTP 인증, STARTTLS와 TLS 1.2를
적용한다. 특정 팀의 실제 SMTP 접속값은 소스나 YAML에 하드코딩하지 않는다.

이 API는 Access Token이 없는 로그인 중간 단계이므로 Spring Security URL 규칙은 `permitAll`이지만,
애플리케이션에서 pre-auth JWT와 Redis 상태를 반드시 검증한다.

## OTP 검증과 최종 로그인

`POST /api/v1/auth/otp/verify`는 pre-auth token과 6자리 OTP를 받는다.

1. pre-auth JWT와 Redis 상태를 교차 검증한다.
2. 사용자와 역할의 현재 활성 상태를 다시 확인한다.
3. 로그인 단계의 최근 접속 사유를 조회한다.
4. TOTP를 검증한다.
5. 실패하면 Redis 실패 횟수를 원자적으로 증가시키고 OTP 실패 이력을 저장한다.
6. 최대 실패 횟수에 도달하면 Redis 사전 인증 상태를 삭제한다.
7. 성공하면 사용자와 목적이 일치하는 사전 인증 상태를 원자적으로 소비해 재사용을 막는다.
8. Access/Refresh Token을 발급하고 사용자별 Refresh Token 해시를 Redis에 저장한다.
9. 최종 로그인 시각과 OTP 성공 이력을 저장한다.

응답 JSON에는 Access Token만 포함한다. Refresh Token은 `Set-Cookie` 헤더의 HttpOnly 쿠키로 발급한다.
메뉴 목록은 로그인 결과에 포함하지 않고 `GET /api/v1/menus/me`에서 별도 조회한다.

## 토큰 종류

| 토큰 | 기본 만료 | 전달 방식 | 서버 상태 |
|---|---:|---|---|
| pre-auth JWT | 5분 | OTP 요청 본문 | Redis `admin-core:pre-auth:{jti}` |
| Access JWT | 30분 | `Authorization: Bearer` 헤더 | 별도 저장하지 않음 |
| Refresh JWT | 7일 | HttpOnly 쿠키 | Redis `admin-core:refresh:{userId}`에 SHA-256 해시 저장 |

JWT는 설정된 HMAC 비밀키로 서명하며 검증 시 서명, 발급자, 만료시간과 `type` 클레임을 확인한다.

## Refresh Token 쿠키

Refresh Token 쿠키 로직은 HTTP 입력 어댑터에 귀속한다.

```text
adapter.in.web.auth.cookie
├─ RefreshTokenCookie
└─ RefreshTokenCookieProperties
```

기본 설정은 다음과 같다.

| 속성 | 값 |
|---|---|
| 이름 | `admin_refresh_token` |
| HttpOnly | `true` |
| Secure | 기본 `true`, local 프로파일 `false` |
| SameSite | `Strict` |
| Path | `/api/v1/auth` |
| Max-Age | Refresh Token 만료시간과 동일 |

`LoginResult`는 Application 내부에서 Refresh Token을 운반하지만 `LoginResponse`는 이를 JSON 필드로 노출하지 않는다.
`AuthController`가 `RefreshTokenCookie`를 통해 OTP 성공·갱신 응답에 쿠키를 추가한다.

## CSRF

Refresh Token 쿠키는 브라우저가 자동 전송하므로 다음 두 요청만 CSRF 보호 대상으로 지정한다.

- `POST /api/v1/auth/refresh`
- `POST /api/v1/auth/logout`

클라이언트 흐름:

```text
GET /api/v1/auth/csrf
  ↓ token, headerName 응답
POST /api/v1/auth/refresh 또는 /logout
  ├─ Cookie: admin_refresh_token=...
  └─ X-XSRF-TOKEN: {token}
```

`CookieCsrfTokenRepository.withHttpOnlyFalse()`가 사용하는 CSRF 쿠키와 HttpOnly Refresh Token 쿠키는 서로 다른
쿠키다. 일반 Bearer Access Token 요청은 현재 CSRF 보호 대상이 아니다.

## 토큰 갱신과 로그아웃

`TokenSessionService`는 Access Token을 요구하지 않고 쿠키의 Refresh Token으로 세션 상태를 처리한다.

### 갱신

1. Refresh JWT의 존재, 만료, 서명, 발급자와 `type=REFRESH`를 검증한다.
2. 토큰 subject의 사용자를 조회하고 사용자·역할의 현재 활성 상태를 확인한다.
3. 새 Access/Refresh Token을 발급한다.
4. Redis에 저장된 기존 해시가 요청 토큰의 SHA-256 해시와 일치할 때만 새 해시와 TTL로 교체한다.
5. 새 Access Token은 JSON으로, 새 Refresh Token은 HttpOnly 쿠키로 반환한다.

### 로그아웃

1. 쿠키가 없거나 유효하지 않은 Refresh JWT이면 서버 상태 변경 없이 쿠키만 만료한다.
2. 유효하면 사용자 ID와 토큰 해시가 Redis 현재 값과 일치할 때만 상태를 삭제한다.
3. 응답에서 같은 이름과 Path의 Max-Age 0 쿠키를 내려 브라우저 쿠키를 제거한다.

Refresh Token 원문은 Redis에 저장하지 않는다. SHA-256은 복호화하기 위한 암호화가 아니라, 요청으로 다시 받은
원문을 같은 방식으로 해시해 저장값과 비교하기 위한 단방향 검증값이다.

## Redis Repository와 원자 연산

일반 저장·조회는 Spring Data Redis Repository 방식으로 처리한다.

```text
@RedisHash Entity
  ↓
ListCrudRepository
  ↓
Redis Adapter
  ↓
Application Port
```

여러 Redis 명령이 하나의 조건부 연산이어야 하는 부분만 Repository Fragment와 Lua Script를 사용한다.

| Fragment | 원자 연산 |
|---|---|
| `PreAuthStateRedisAtomicOperationsImpl` | OTP 실패 횟수 증가 후 한도 도달 시 삭제, 사용자·목적 확인 후 소비 |
| `RefreshTokenRedisAtomicOperationsImpl` | 기존 해시 비교 후 새 해시·TTL 교체, 해시 비교 후 삭제 |

Lua Script는 별도 리소스 파일이 아니라 구현 클래스의 `RedisScript<Long>` 상수에 Java Text Block으로 선언한다.
`StringRedisTemplate`은 Repository가 표현하기 어려운 이 원자 연산을 실행하기 위해 Fragment 내부에서만 사용한다.

## 매 요청 Access Token 인증

`JwtAuthenticationFilter`는 `OncePerRequestFilter`로 등록되어 Controller보다 먼저 실행된다.

1. `Authorization` 헤더가 `Bearer `로 시작하는지 확인한다.
2. `AccessTokenAuthenticationUseCase.authenticate(token)`을 호출한다.
3. JWT 서명·발급자·만료·`type=ACCESS`를 검증한다.
4. 토큰 subject의 사용자를 DB에서 다시 조회하고 활성 상태를 검사한다.
5. 사용자의 현재 역할을 DB에서 다시 조회하고 활성 상태를 검사한다.
6. 검증된 결과를 `AdminPrincipal`과 인증된 `UsernamePasswordAuthenticationToken`으로 변환한다.
7. 인증 객체를 `SecurityContextHolder`에 저장하고 다음 필터로 전달한다.

토큰 또는 현재 계정 검증 중 `RuntimeException`이 발생하면 필터는 SecurityContext를 비우고 요청을 계속 전달한다.
보호 URL은 이후 인가 단계에서 미인증으로 판단되어 `RestAuthenticationEntryPoint`의 JSON 401 응답을 받는다.
공개 URL은 Access Token이 없어도 계속 처리된다.

`AdminPrincipal`은 Spring Security 전용 입력 어댑터 모델이며 application/domain 계층에 노출하지 않는다.

## URL 인가와 메뉴 권한

`SecurityConfig`는 URL별 정책을 위에서 아래로 선언하며 먼저 일치한 규칙을 적용한다.

```text
SecurityConfig
  ↓ MenuPermissionAuthorizationManagerFactory
MenuPermissionAuthorizationManager
  ↓ CheckMenuPermissionUseCase
MenuPermissionAuthorizationService
```

- `MenuPermissionAuthorizationManager`는 `AdminPrincipal`의 사용자 ID를 권한 Query로 변환한다.
- Application Service는 사용자, 현재 역할, 역할별 메뉴 권한을 DB에서 조회한다.
- 후보 메뉴 중 하나가 요청한 `VIEW` 또는 `EDIT`를 허용하면 접근을 허용한다.
- `canEdit=true`는 `canView=true`와 함께만 생성할 수 있다.
- 인증됐지만 권한이 부족하면 `RestAccessDeniedHandler`가 JSON 403을 반환한다.

`GET /api/v1/menus/me`는 인증 사용자 ID로 `MenuService`를 직접 호출한다. 조회 가능한 메뉴와 화면 계층에 필요한
상위 메뉴를 조합해 반환하며, 다른 Application Service를 호출하지 않는다.

현재 메뉴 권한이 필요한 요청은 인증 단계와 인가 단계가 각각 사용자·역할의 최신 상태를 조회한다. 즉시 비활성화를
반영하는 대신 사용자·역할 조회가 중복될 수 있다는 현재 설계의 비용이 있다.

## 신규 API 개발 시 SecurityConfig 등록 규칙

새 Controller API를 추가하면 먼저 해당 API가 공개 API인지, 로그인 사용자 공통 API인지, 메뉴 권한이 필요한 업무
API인지 결정한다. `JwtAuthenticationFilter`는 전체 요청에 이미 적용되므로 API마다 필터를 추가하지 않는다.

### 접근 정책 선택

| API 성격 | SecurityConfig 규칙 | 사용 예 |
|---|---|---|
| Access Token 없이 호출해야 하는 인증 시작·중간 API | `permitAll()` | 로그인, OTP 등록·검증, Refresh, 로그아웃, CSRF 토큰 발급 |
| 로그인한 사용자라면 공통으로 사용할 수 있는 API | `authenticated()` | 내 메뉴 조회 |
| 업무 데이터 조회 API | `permissions.canView("메뉴 코드")` | 사용자·역할·로그인 이력·파일 이력 조회 |
| 업무 데이터 생성·수정·삭제 API | `permissions.canEdit("메뉴 코드")` | 사용자 등록·수정, 비밀번호 초기화, 역할·권한 변경 |
| 둘 이상의 메뉴 중 하나의 조회 권한으로 호출 가능한 공통 API | `permissions.canView("코드1", "코드2")` | 사용자 화면과 역할 화면에서 함께 사용하는 활성 역할 목록 |

`permitAll()`은 Spring Security의 Access Token 검사를 생략해도 된다는 뜻이다. 인증 자체가 필요 없다는 뜻은 아니다.
OTP API는 Pre-Auth JWT와 Redis 상태를 Application Service에서 검증하고, Refresh와 로그아웃은 HttpOnly 쿠키의
Refresh Token을 검증한다. 일반 업무 API를 편의상 `permitAll()`로 등록하지 않는다.

### 조회와 변경 API 등록 예시

예를 들어 `REPORTS` 메뉴에 다음 API를 추가한다고 가정한다.

```text
GET    /api/v1/reports       목록 조회
GET    /api/v1/reports/{id}  상세 조회
POST   /api/v1/reports       등록
PATCH  /api/v1/reports/{id}  수정
DELETE /api/v1/reports/{id}  삭제
```

`SecurityConfig`의 `authorizeHttpRequests`에 조회 규칙을 먼저, 변경 규칙을 다음에 선언한다.

```java
.requestMatchers(HttpMethod.GET, "/api/v1/reports", "/api/v1/reports/**")
        .access(permissions.canView("REPORTS"))
.requestMatchers("/api/v1/reports", "/api/v1/reports/**")
        .access(permissions.canEdit("REPORTS"))
```

Spring Security는 위에서 아래로 요청과 처음 일치한 규칙을 적용한다. 메서드를 제한하지 않은 두 번째 규칙을 먼저
선언하면 GET 요청까지 `EDIT` 권한을 요구하므로 반드시 GET 조회 규칙을 앞에 둔다. 컬렉션 경로와 하위 경로를 모두
보호하려면 `"/api/v1/reports"`와 `"/api/v1/reports/**"`를 함께 등록한다.

마지막의 `.anyRequest().authenticated()`는 명시하지 않은 API에도 로그인만 요구하는 안전망이다. 메뉴 권한까지
검사하지는 않으므로 신규 업무 API를 이 규칙에만 맡기면 안 된다.

### 기존 메뉴에 API를 추가하는 경우

기존 메뉴 기능을 확장하면 해당 메뉴 코드를 그대로 사용한다.

```java
// 사용자 목록과 상세 조회
.requestMatchers(HttpMethod.GET, "/api/v1/users", "/api/v1/users/**")
        .access(permissions.canView("USERS"))

// 사용자 등록·수정·비밀번호 초기화 등 상태 변경
.requestMatchers("/api/v1/users", "/api/v1/users/**")
        .access(permissions.canEdit("USERS"))
```

메뉴 코드는 화면 이름을 임의로 문자열로 적는 값이 아니라 `AdminMenuDefinition`과 `permissions.menu_code`가 공유하는
식별자다. 오탈자가 있으면 모든 사용자의 권한 검사가 실패하므로 현재 정의된 코드를 그대로 사용한다.

| 메뉴 | SecurityConfig에서 사용하는 코드 |
|---|---|
| 사용자 관리 | `USERS` |
| 권한 관리 | `ROLES` |
| 로그인 이력 조회 | `LOGIN_HISTORY` |
| 파일 이력 조회 | `FILE_HISTORY` |

### 새로운 메뉴와 업무 API를 함께 추가하는 경우

새로운 메뉴 코드를 도입할 때는 `SecurityConfig`만 수정해서는 안 된다. 다음 항목을 함께 반영한다.

1. `AdminMenuDefinition`에 메뉴 코드, 이름, 프론트 경로, 상위 메뉴와 표시 순서를 추가한다.
2. 역할에 새 메뉴 코드의 `can_view`, `can_edit` 권한을 부여할 수 있도록 초기 데이터 또는 운영 배포 SQL을 작성한다.
3. `SecurityConfig`에 HTTP Method별 `canView`와 `canEdit` 규칙을 추가한다.
4. API 정의서와 메뉴·권한 관련 테스트에 새 API와 메뉴 코드를 반영한다.

DB 권한 데이터가 없으면 `SecurityConfig`에 올바른 메뉴 코드를 등록해도 접근은 거부된다. 메뉴 정의, 역할별 DB 권한,
URL 인가 규칙이 같은 코드를 사용해야 한다.

### 공개 API를 추가하는 경우

정말 Access Token 없이 호출해야 하는 경로만 기존 공개 경로 묶음에 추가한다.

```java
.requestMatchers(
        "/api/v1/auth/login",
        "/api/v1/auth/refresh",
        "/api/v1/auth/logout",
        "/api/v1/auth/csrf",
        "/api/v1/auth/otp/barcode",
        "/api/v1/auth/otp/verify",
        "/api/v1/auth/new-public-endpoint"
).permitAll()
```

공개 경로에서도 Request DTO 검증, Pre-Auth·Refresh Token 검증, 실패 횟수 제한 같은 해당 유스케이스의 보안 규칙은
Application Service에서 수행한다. `permitAll()`로 등록했다는 이유로 검증 로직을 Controller에 작성하거나 생략하지
않는다.

### Refresh Token 쿠키를 사용하는 변경 API

현재 CSRF 보호 대상은 브라우저가 HttpOnly Refresh Token 쿠키를 자동 전송하는 다음 API다.

```java
.requireCsrfProtectionMatcher(new OrRequestMatcher(
        new AntPathRequestMatcher("/api/v1/auth/refresh", "POST"),
        new AntPathRequestMatcher("/api/v1/auth/logout", "POST")
))
```

새 API가 쿠키 인증으로 서버 상태를 변경한다면 위 `OrRequestMatcher`에 정확한 경로와 HTTP Method를 추가하고,
클라이언트가 `/api/v1/auth/csrf`에서 받은 토큰을 `X-XSRF-TOKEN` 헤더로 전달하게 해야 한다. Bearer Access Token만
사용하는 일반 업무 API는 브라우저가 토큰을 자동 전송하지 않으므로 현재 설정에서 이 목록에 추가하지 않는다.

### CORS 설정을 함께 변경해야 하는 경우

일반적인 JSON API는 이미 허용된 `GET`, `POST`, `PUT`, `PATCH`, `DELETE` Method와 `Authorization`,
`Content-Type`, `X-XSRF-TOKEN` 헤더를 사용하므로 CORS 설정을 바꾸지 않는다.

#### CORS 설정 위치

| 역할 | 정확한 위치 | 내용 |
|---|---|---|
| 공통값과 로컬 기본값 | `src/main/resources/application.yml` | 활성 Profile 기본값과 `security.cors.allowed-origins` 선언 |
| 로컬 Profile | `src/main/resources/application-local.yml` | 로컬 DB·Redis와 쿠키 설정만 재정의하며 CORS는 공통값 상속 |
| 개발 Profile | `src/main/resources/application-dev.yml` | 개발 환경의 필수 `ADMIN_FRONTEND_ORIGIN` 사용 |
| 운영 Profile | `src/main/resources/application-prod.yml` | 운영 환경의 필수 `ADMIN_FRONTEND_ORIGIN` 사용 |
| 설정 객체 | `src/main/java/com/espay/admincore/config/CorsProperties.java` | YAML의 Origin 목록을 `List<String>`으로 바인딩하고 빈 목록과 `*` 거부 |
| CORS 적용 | `src/main/java/com/espay/admincore/config/SecurityConfig.java` | 허용 Origin·Method·Header·Credential과 적용 URL 설정 |

#### 설정 파일 구조

`application.yml`은 모든 환경에 먼저 적용되는 공통 설정이다. `SPRING_PROFILES_ACTIVE`가 없으면 `local`을 활성화하고,
로컬 프론트엔드 Origin 기본값으로 `http://localhost:13010`을 사용한다.

```yaml
spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:local}

security:
  cors:
    allowed-origins:
      - ${ADMIN_FRONTEND_ORIGIN:http://localhost:13010}
```

`application-local.yml`에는 `security.cors`가 없다. 따라서 `local` 실행 시에는 `application.yml`과
`application-local.yml`이 함께 적용되지만 CORS 값은 `application.yml`의 값을 그대로 사용한다.

```text
application.yml
  security.cors.allowed-origins = http://localhost:13010

application-local.yml
  security.cors 설정 없음

최종 local CORS Origin
  http://localhost:13010
```

`application-dev.yml`과 `application-prod.yml`은 공통 CORS 목록을 같은 경로로 재정의한다. 두 Profile은 기본 Origin을
두지 않으므로 `ADMIN_FRONTEND_ORIGIN`이 설정되지 않으면 애플리케이션을 정상적으로 시작할 수 없다.

```yaml
# application-dev.yml과 application-prod.yml
security:
  cors:
    allowed-origins:
      - ${ADMIN_FRONTEND_ORIGIN}
```

| 실행 환경 | 함께 읽는 파일 | 최종 Origin 결정 방식 |
|---|---|---|
| 로컬 | `application.yml` + `application-local.yml` | 환경 변수가 없으면 `http://localhost:13010`, 있으면 해당 값 |
| 개발 | `application.yml` + `application-dev.yml` | 개발 서버의 `ADMIN_FRONTEND_ORIGIN` 값이 필수 |
| 운영 | `application.yml` + `application-prod.yml` | 운영 서버의 `ADMIN_FRONTEND_ORIGIN` 값이 필수 |

같은 설정 경로가 두 파일에 있으면 활성 Profile 파일의 값이 공통 파일보다 우선한다. 실행 시 주입한 환경 변수는 YAML의
`${ADMIN_FRONTEND_ORIGIN...}` 자리에 들어가므로 소스 파일을 환경마다 수정할 필요가 없다.

#### 설정 객체와 SecurityConfig 적용 구조

`AdminCoreApplication`의 `@ConfigurationPropertiesScan`이 다음 `CorsProperties`를 등록한다. YAML의
`security.cors.allowed-origins`는 `allowedOrigins` 필드로 바인딩된다.

```java
@ConfigurationProperties("security.cors")
public record CorsProperties(List<String> allowedOrigins) {
    public CorsProperties {
        allowedOrigins = allowedOrigins == null ? List.of() : List.copyOf(allowedOrigins);
        if (allowedOrigins.isEmpty() || allowedOrigins.stream().anyMatch("*"::equals)) {
            throw new IllegalArgumentException("CORS 허용 Origin은 정확한 주소로 한 개 이상 설정해야 합니다.");
        }
    }
}
```

`SecurityConfig`는 바인딩된 목록을 Spring Security의 `CorsConfiguration`에 전달하고 `/api/**` 요청에 적용한다.

```java
CorsConfiguration configuration = new CorsConfiguration();
configuration.setAllowedOrigins(corsProperties.allowedOrigins());
configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"));
configuration.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-XSRF-TOKEN"));
configuration.setAllowCredentials(true);
configuration.setMaxAge(3600L);

UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
source.registerCorsConfiguration("/api/**", configuration);
```

전체 적용 흐름은 다음과 같다.

```text
application.yml
  + application-{활성 Profile}.yml
  + ADMIN_FRONTEND_ORIGIN 환경 변수
            ↓
security.cors.allowed-origins
            ↓
CorsProperties.allowedOrigins
            ↓
SecurityConfig.corsConfigurationSource()
            ↓
/api/** 요청의 CORS 검사
```

#### 환경별 적용 방법

로컬 프론트엔드가 기본값과 다른 `http://localhost:3000`에서 실행된다면 백엔드를 실행하는 같은 터미널에서 값을
재정의한다.

```powershell
$env:SPRING_PROFILES_ACTIVE='local'
$env:ADMIN_FRONTEND_ORIGIN='http://localhost:3000'
.\gradlew.bat bootRun
```

개발과 운영은 Docker Compose, Kubernetes, 배포 스크립트 또는 서버 환경 변수에서 실제 프론트엔드 Origin을 주입한다.

```text
# 개발 환경
SPRING_PROFILES_ACTIVE=dev
ADMIN_FRONTEND_ORIGIN=https://dev-admin.example.com

# 운영 환경
SPRING_PROFILES_ACTIVE=prod
ADMIN_FRONTEND_ORIGIN=https://admin.example.com
```

Origin은 브라우저의 `Origin` 헤더와 정확히 같아야 한다. 프로토콜, 호스트와 포트만 작성하며 URL 경로나 마지막 `/`는
붙이지 않는다. 예를 들어 `https://admin.example.com/app`이 아니라 `https://admin.example.com`을 등록한다.

#### 한 환경에서 여러 Origin을 허용하는 경우

현재 설정은 환경마다 한 개의 프론트엔드 Origin을 주입한다. 같은 환경에서 두 개 이상의 프론트엔드를 동시에 허용해야
한다면 해당 Profile YAML의 목록에 별도 환경 변수를 추가한다.

```yaml
security:
  cors:
    allowed-origins:
      - ${ADMIN_FRONTEND_ORIGIN}
      - ${ADMIN_FRONTEND_ORIGIN_SECONDARY}
```

이 경우 두 환경 변수를 모두 설정해야 한다. 현재 YAML 구조에서 `ADMIN_FRONTEND_ORIGIN` 하나에 주소를 쉼표로 연결하면
두 Origin이 아니라 하나의 문자열로 인식되므로 사용하지 않는다. `allowCredentials=true`인 쿠키 요청에서는 `*`도
허용하지 않으며 `CorsProperties`가 애플리케이션 시작 시 이를 거부한다.

#### Header와 응답 노출 설정

- 새로운 사용자 정의 요청 헤더가 반드시 필요하면 `corsConfigurationSource()`의 `allowedHeaders`에도 추가한다.
- 서버 응답 헤더를 브라우저 JavaScript에서 읽어야 하면 필요한 헤더만 `exposedHeaders`로 명시한다.
- 임의의 전체 Origin이나 전체 Header 허용으로 해결하지 않는다.

### 개발 완료 확인 항목

| 확인 요청 | 기대 결과 |
|---|---|
| Access Token 없이 보호 API 호출 | `401 UNAUTHORIZED` |
| 유효한 Access Token, 메뉴 권한 없음 | `403 FORBIDDEN` |
| `VIEW`만 있는 사용자로 GET 호출 | 성공 |
| `VIEW`만 있는 사용자로 POST·PUT·PATCH·DELETE 호출 | `403 FORBIDDEN` |
| `EDIT` 권한이 있는 사용자로 변경 API 호출 | 성공 |
| 비활성 사용자 또는 비활성 역할의 토큰으로 호출 | `401 UNAUTHORIZED` |
| 공개 API를 Access Token 없이 호출 | Spring Security 통과 후 해당 유스케이스 검증 수행 |

신규 API 테스트에서는 URL만 확인하지 말고 HTTP Method와 권한 조합을 함께 검증한다. 특히 GET 규칙과 변경 규칙의
선언 순서가 바뀌어 조회에 `EDIT` 권한을 요구하지 않는지 확인한다.

## CORS와 설정 소유권

포괄적인 `SecurityWebProperties`는 사용하지 않는다.

- `config.CorsProperties`: 부트스트랩 보안 설정이 허용 Origin을 관리한다.
- `adapter.in.web.auth.cookie.RefreshTokenCookieProperties`: Refresh Token HTTP 쿠키 설정을 관리한다.

CORS는 `/api/**`에만 적용되며 정확히 등록된 Origin, `Authorization`, `Content-Type`, `X-XSRF-TOKEN` 헤더와
브라우저 Credential 전송을 허용한다. 모든 OPTIONS 사전 요청은 공개한다.

## 패키지 구조

Application Service와 Domain Model은 업무 단위로 구분한다.

```text
application.service
├─ auth
├─ history
├─ menu
├─ role
└─ user

domain.model
├─ file
├─ history
├─ menu
├─ role
└─ user
```

Spring Security와 Spring MVC 입력 구성요소는 다음과 같이 나눈다.

```text
adapter.in
├─ security
│  ├─ authentication
│  │  ├─ AdminPrincipal
│  │  ├─ JwtAuthenticationFilter
│  │  └─ RestAuthenticationEntryPoint
│  └─ authorization
│     ├─ MenuPermissionAuthorizationManager
│     ├─ MenuPermissionAuthorizationManagerFactory
│     └─ RestAccessDeniedHandler
└─ web
   ├─ auth
   │  └─ cookie
   ├─ history
   ├─ menu
   ├─ role
   ├─ user
   └─ resolver
```

- `security.authentication`: Access Token을 검증하고 SecurityContext를 구성한다.
- `security.authorization`: 메뉴 권한을 검사하고 인가 실패를 처리한다.
- `web.auth.cookie`: Refresh Token을 HTTP 쿠키로 발급·만료한다.
- `web.resolver`: 요청 IP와 인증 사용자 ID를 Controller 파라미터로 변환한다.
- `web.*`: HTTP Request를 Command/Query로, Application 결과를 HTTP Response로 변환한다.

## 트랜잭션 경계

Application Service는 별도의 `ApplicationServiceConfig`, `ApplicationTransactionConfig`로 조립하지 않는다.

- 각 서비스는 `@Service`로 Component Scan된다.
- 트랜잭션은 클래스가 아니라 유스케이스 메서드에 직접 선언한다.
- 조회는 `@Transactional(readOnly = true)`, DB 변경은 `@Transactional`을 사용한다.
- Redis 세션 상태를 처리하는 `TokenSessionService`에는 JPA 트랜잭션을 선언하지 않는다.
- 로그인·파일 감사 이력의 `save()`는 Persistence Adapter에 `REQUIRES_NEW`를 선언해 호출 업무와 별도로 커밋한다.

감사 이력 Port는 `LoginHistory`, `FileHistory` Aggregate를 직접 저장한다. 중계용
`RecordLoginHistoryCommand`, `*CreateData`, `*UpdateData`는 사용하지 않는다.

## 계층 의존성

```text
adapter.in.security ──→ application ──→ domain
adapter.in.web      ──→ application ──→ domain
adapter.out         ──→ application ──→ domain
config              ──→ application / adapter
```

- domain은 Spring, Jakarta, application, adapter, config, common 패키지를 참조하지 않는다.
- application은 Jakarta, adapter, config 패키지를 참조하지 않는다.
- application에서 허용하는 Spring 의존성은 `@Service`와 메서드 단위 `@Transactional`뿐이다.
- Application Service는 다른 입력 UseCase Port를 주입받지 않는다.
- 입출력 경계를 통과하는 인증 결과와 Command는 application이 소유한다.
- Spring Security Principal, Servlet, MVC 모델은 입력 어댑터가 소유한다.
- `CoreDependencyRuleTest`와 관련 아키텍처 테스트가 이 규칙을 자동 검사한다.
