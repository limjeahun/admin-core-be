# Admin Core 로컬 환경 구성 및 실행 가이드

## 1. 로컬 실행 구조

로컬 환경에서는 MariaDB와 Redis만 Docker Compose로 실행한다. `admin-core-be` 애플리케이션은 Docker 컨테이너로
실행하지 않고 호스트에 설치한 JDK 21과 프로젝트의 Gradle Wrapper로 `bootRun`한다.

```text
호스트 운영체제
├─ JDK 21
│  └─ admin-core-be
│     ├─ API              localhost:10086
│     └─ Actuator         localhost:11086
│
└─ Docker Desktop
   ├─ MariaDB 11.4        localhost:13308 → container:3306
   └─ Redis 7.4           localhost:16380 → container:6379
```

`infra/local/docker-compose.yml`에는 `mariadb`, `redis` 두 서비스만 존재한다. 애플리케이션 서비스는 추가하지 않는다.

| 구분 | 실행 위치 | 실행 방법 |
|---|---|---|
| MariaDB | Docker Desktop | `docker compose up -d` |
| Redis | Docker Desktop | `docker compose up -d` |
| Admin Core API | Windows 또는 macOS 호스트 | Gradle Wrapper의 `bootRun` |

## 2. 필요한 프로그램과 포트

### 2.1 필수 프로그램

| 프로그램 | 용도 | 설치 여부 |
|---|---|---|
| JDK 21 | Spring Boot 컴파일과 실행 | 필수 |
| Docker Desktop | MariaDB와 Redis 컨테이너 실행 | 필수 |
| Git | 저장소를 새로 내려받을 때 사용 | 프로젝트가 이미 있으면 선택 |
| IntelliJ IDEA 등 IDE | 코드 편집과 디버깅 | 선택 |
| DBeaver 또는 DataGrip | DB 내용을 GUI로 확인 | 선택 |

Gradle, MariaDB와 Redis는 호스트에 별도로 설치하지 않는다.

- Gradle은 저장소의 `gradlew`, `gradlew.bat`과 `gradle/wrapper`를 사용한다.
- MariaDB와 Redis는 `infra/local/docker-compose.yml`이 필요한 이미지를 내려받아 실행한다.
- Gradle Wrapper의 최초 실행에는 Gradle 배포 파일과 의존성을 내려받기 위한 인터넷 연결이 필요하다.

Gradle Wrapper를 사용하는 이유와 동작 방식은 [Gradle 공식 Wrapper 문서](https://docs.gradle.org/current/userguide/gradle_wrapper.html)에서 확인할 수 있다.

### 2.2 사용 포트

다음 포트를 다른 프로그램이 사용하고 있지 않아야 한다.

| 대상 | 호스트 포트 | 컨테이너 내부 포트 |
|---|---:|---:|
| Admin Core API | `10086` | - |
| Actuator | `11086` | - |
| MariaDB | `13308` | `3306` |
| Redis | `16380` | `6379` |
| 로컬 프론트엔드 Origin | `13010` | - |

프론트엔드는 이 저장소에서 실행하지 않는다. `13010`은 백엔드가 기본적으로 허용하는 로컬 CORS Origin의 포트다.

## 3. Windows 설치

모든 프로젝트 명령은 PowerShell을 기준으로 한다.

### 3.1 JDK 21 설치

이 가이드는 JDK 21 배포판 중 Eclipse Temurin 설치를 기준으로 한다. 이미 호환되는 다른 JDK 21이 설치되어 있다면
다시 설치할 필요는 없다. JRE만으로는 빌드할 수 없으므로 반드시 JDK가 필요하다.

#### Winget으로 설치

PowerShell에서 다음 명령을 실행한다.

```powershell
winget install --id EclipseAdoptium.Temurin.21.JDK --exact
```

#### MSI로 설치

1. [Eclipse Temurin JDK 21 다운로드](https://adoptium.net/temurin/releases/?version=21&package=jdk)에서 Windows x64 JDK MSI를 받는다.
2. MSI 설치 화면에서 `PATH` 추가를 활성화한다.
3. `JAVA_HOME` 갱신 항목도 활성화한다.
4. 설치가 끝나면 기존 PowerShell을 닫고 새 PowerShell을 연다.

Windows MSI의 세부 설치 항목은 [Adoptium 공식 Windows 설치 문서](https://adoptium.net/installation/windows/)에서
확인한다.

설치 결과를 확인한다.

```powershell
java -version
$env:JAVA_HOME
```

`java -version`에는 `21`이 표시되어야 한다. 다른 Java 버전이 표시되면 `JAVA_HOME`과 `Path`에서 JDK 21이 먼저
선택되도록 수정한 후 PowerShell을 다시 연다.

### 3.2 Docker Desktop 설치

1. BIOS/UEFI에서 하드웨어 가상화가 활성화되어 있는지 확인한다.
2. WSL 2가 없다면 관리자 PowerShell에서 다음 명령을 실행하고 Windows를 재시작한다.

```powershell
wsl --install
```

3. [Docker Desktop for Windows 공식 설치 문서](https://docs.docker.com/desktop/setup/install/windows-install/)에서
   Docker Desktop을 설치한다.
4. WSL 2 Backend를 사용한다.
5. Docker Desktop을 실행하고 Engine 시작이 완료될 때까지 기다린다.

WSL 설치와 상태 확인 방법은 [Microsoft WSL 설치 문서](https://learn.microsoft.com/windows/wsl/install)를 따른다.

새 PowerShell에서 Docker와 Compose를 확인한다.

```powershell
docker version
docker compose version
wsl --status
```

`docker version`에서 Server 정보까지 출력되어야 한다. Client만 나오고 Server 연결 오류가 발생하면 Docker Desktop이
실행되지 않았거나 Engine 초기화가 끝나지 않은 상태다.

## 4. macOS 설치

모든 프로젝트 명령은 Terminal의 zsh를 기준으로 한다.

### 4.1 Mac CPU 확인

다음 명령으로 설치 파일의 아키텍처를 결정한다.

```bash
uname -m
```

| 출력 | Mac 종류 | 선택할 설치 파일 |
|---|---|---|
| `arm64` | Apple Silicon | Apple Silicon 또는 AArch64 |
| `x86_64` | Intel Mac | Intel 또는 x64 |

### 4.2 JDK 21 설치

1. [Eclipse Temurin JDK 21 다운로드](https://adoptium.net/temurin/releases/?version=21&package=jdk)에서 Mac 종류에 맞는
   JDK 21 `.pkg`를 받는다.
2. `.pkg`를 실행해 설치한다.
3. 새 Terminal을 열고 Java 버전을 확인한다.

상세 절차는 [Adoptium 공식 macOS 설치 문서](https://adoptium.net/installation/macOS/)를 따른다.

```bash
java -version
/usr/libexec/java_home -v 21
```

현재 Terminal이 JDK 21을 선택하지 않는다면 다음 값을 `~/.zshrc`에 추가하고 새 Terminal을 연다.

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)
export PATH="$JAVA_HOME/bin:$PATH"
```

### 4.3 Docker Desktop 설치

1. [Docker Desktop for Mac 공식 설치 문서](https://docs.docker.com/desktop/setup/install/mac-install/)에서 Apple
   Silicon 또는 Intel용 DMG를 받는다.
2. `Docker.dmg`를 열고 Docker 아이콘을 `Applications`로 이동한다.
3. `Applications/Docker.app`을 실행한다.
4. Engine 시작이 완료될 때까지 기다린다.

Terminal에서 설치 결과를 확인한다.

```bash
docker version
docker compose version
```

`docker version`에서 Server 정보까지 출력되어야 한다.

## 6. MariaDB와 Redis 실행

### 6.1 Compose 구성

`infra/local/docker-compose.yml`은 다음 자원을 생성한다.

| 서비스 | 이미지 | 컨테이너 | 포트 | 데이터 Volume |
|---|---|---|---|---|
| MariaDB | `mariadb:11.4` | `admin-core-mariadb` | `13308:3306` | `admin-core-mariadb-data` |
| Redis | `redis:7.4-alpine` | `admin-core-redis` | `16380:6379` | `admin-core-redis-data` |

MariaDB 로컬 초기값:

| 항목 | 값 |
|---|---|
| Database | `admin_core` |
| Username | `admin_core` |
| Password | `admin_core` |
| Root Password | `admin_core` |
| Timezone | `Asia/Seoul` |

Redis는 AOF를 활성화해 데이터를 Volume의 `/data`에 보존한다.

### 6.2 컨테이너 시작

Windows PowerShell과 macOS Terminal 모두 아래 명령을 동일하게 사용할 수 있다.

#### 1단계: Docker Engine 실행 확인

Docker Desktop을 먼저 실행한 후 다음 명령을 입력한다.

```bash
docker version
docker compose version
```

- `docker version`: Docker Client와 Docker Engine Server의 버전을 확인한다.
- `docker compose version`: Compose V2 명령을 사용할 수 있는지 확인한다.

`docker version`에서 Client 정보만 나오고 Server 연결 오류가 발생하면 컨테이너를 시작할 수 없다. Docker Desktop의
Engine 시작이 끝난 뒤 다시 실행한다.

#### 2단계: 프로젝트 루트와 Compose 파일 확인

프로젝트 루트에서 실행한다.

Windows:

```powershell
cd D:/workspace/admin-core-be
Test-Path ./infra/local/docker-compose.yml
```

macOS:

```bash
cd ~/workspace/admin-core-be
test -f ./infra/local/docker-compose.yml && echo "compose file exists"
```

Compose 파일의 문법과 Docker가 해석한 최종 설정을 실행 전에 확인한다.

```bash
docker compose -f infra/local/docker-compose.yml config
```

`config`는 설정을 출력할 뿐 이미지, 컨테이너, 네트워크와 Volume을 생성하지 않는다. 출력에 `mariadb`와 `redis`
서비스, `13308:3306`과 `16380:6379` 포트가 있는지 확인한다.

명령 구성:

| 부분 | 의미 |
|---|---|
| `docker` | Docker CLI 실행 |
| `compose` | 여러 컨테이너를 Compose 파일 기준으로 관리 |
| `-f infra/local/docker-compose.yml` | 프로젝트 루트가 아닌 하위 경로의 Compose 파일을 명시 |
| `config` | Compose 문법과 최종 병합 결과 확인 |

프로젝트 루트에는 Compose 파일이 없으므로 루트에서 `-f infra/local/docker-compose.yml`을 생략하지 않는다.

#### 3단계: MariaDB와 Redis 이미지 받기

```bash
docker compose -f infra/local/docker-compose.yml pull
```

`pull`은 Compose에 선언된 `mariadb:11.4`와 `redis:7.4-alpine` 이미지를 Docker Registry에서 내려받지만
컨테이너는 시작하지 않는다. 이미 같은 이미지가 있으면 다시 받을 레이어 없이 완료된다.

특정 서비스 이미지만 받으려면 서비스명을 마지막에 지정한다.

```bash
docker compose -f infra/local/docker-compose.yml pull mariadb
docker compose -f infra/local/docker-compose.yml pull redis
```

`pull` 동작은 [Docker 공식 compose pull 문서](https://docs.docker.com/reference/cli/docker/compose/pull/)에서 확인할 수 있다.

#### 4단계: 두 컨테이너를 백그라운드로 시작

```bash
docker compose -f infra/local/docker-compose.yml up -d
```

명령 구성:

| 부분 | 의미 |
|---|---|
| `up` | Compose 서비스에 필요한 컨테이너, 네트워크와 Volume을 생성하고 시작 |
| `-d` 또는 `--detach` | 로그 화면에 계속 붙어 있지 않고 백그라운드에서 실행 |

이 명령으로 다음 자원이 준비된다.

1. `admin-core-mariadb` 컨테이너를 생성하거나 기존 컨테이너를 시작한다.
2. `admin-core-redis` 컨테이너를 생성하거나 기존 컨테이너를 시작한다.
3. 두 컨테이너가 통신할 Compose 네트워크를 생성한다.
4. MariaDB와 Redis 데이터를 보존할 Named Volume을 생성하거나 기존 Volume을 다시 연결한다.
5. 호스트 `13308`을 MariaDB `3306`에, 호스트 `16380`을 Redis `6379`에 연결한다.

이미 실행 중이고 Compose 설정이 바뀌지 않았다면 컨테이너를 불필요하게 다시 만들지 않는다. Compose 설정이나 이미지가
바뀌었다면 `up`이 필요한 서비스를 다시 생성하고 Named Volume은 보존한다. 세부 동작은
[Docker 공식 compose up 문서](https://docs.docker.com/reference/cli/docker/compose/up/)를 참고한다.

`pull`을 먼저 실행하지 않아도 로컬에 이미지가 없으면 `up`이 필요한 이미지를 받는다. 최초 구성에서는 이미지 다운로드와
컨테이너 시작을 구분해 확인할 수 있도록 `pull`과 `up -d`를 나누어 실행한다.

#### 5단계: 컨테이너와 Health 상태 확인

```bash
docker compose -f infra/local/docker-compose.yml ps
```

`ps`는 이 Compose 프로젝트의 실행 중인 컨테이너, 상태와 공개 포트를 보여준다.

최초 실행은 MariaDB 초기화 때문에 시간이 걸릴 수 있다. `ps` 결과에서 두 서비스가 모두
`healthy`가 될 때까지 기다린다.

```text
admin-core-mariadb   ...   Up ... (healthy)
admin-core-redis     ...   Up ... (healthy)
```

상태 의미:

| 상태 | 의미 | 조치 |
|---|---|---|
| `Up ... (health: starting)` | 컨테이너는 실행됐지만 초기화 중 | 잠시 후 `ps` 재실행 |
| `Up ... (healthy)` | Health Check 통과 | 애플리케이션 실행 가능 |
| `Up ... (unhealthy)` | 실행 중이지만 Health Check 실패 | 서비스 로그 확인 |
| `Exited` | 프로세스 종료 | `ps --all`과 로그로 종료 원인 확인 |

종료된 컨테이너까지 포함해 확인한다.

```bash
docker compose -f infra/local/docker-compose.yml ps --all
```

Compose가 `--wait` 옵션을 지원하면 시작과 Health 대기를 한 명령으로 처리할 수도 있다.

```bash
docker compose -f infra/local/docker-compose.yml up -d --wait --wait-timeout 120
```

`--wait`는 모든 서비스가 실행 또는 `healthy` 상태가 될 때까지 기다리고, `--wait-timeout 120`은 최대 대기 시간을
120초로 제한한다. 기본 실행 절차에서는 상태 변화가 보이도록 `up -d`와 `ps`를 분리한다. `ps`의 상태·포트 출력은
[Docker 공식 compose ps 문서](https://docs.docker.com/reference/cli/docker/compose/ps/)를 참고한다.

#### 6단계: 시작 로그 확인

마지막 100줄을 확인한다.

```bash
docker compose -f infra/local/docker-compose.yml logs --tail=100 mariadb redis
```

새 로그를 계속 확인한다.

```bash
docker compose -f infra/local/docker-compose.yml logs -f --tail=100 mariadb redis
```

`-f`가 Compose 파일 지정 옵션과 로그 추적 옵션에 각각 사용되는 위치가 다르다는 점에 주의한다.

```text
docker compose -f {Compose 파일} logs -f {서비스}
               ↑                    ↑
         Compose 파일 지정          로그 계속 보기
```

로그 추적 화면에서 `Ctrl+C`를 눌러도 `-d`로 실행한 MariaDB와 Redis 컨테이너는 종료되지 않는다. 로그 옵션은
[Docker 공식 compose logs 문서](https://docs.docker.com/reference/cli/docker/compose/logs/)를 참고한다.

#### 이후 매일 실행하는 명령

이미 이미지, 컨테이너와 Volume이 만들어진 이후에는 다음 두 명령이면 충분하다.

```bash
docker compose -f infra/local/docker-compose.yml up -d
docker compose -f infra/local/docker-compose.yml ps
```

`up -d`는 컨테이너가 정지돼 있으면 시작하고 이미 실행 중이면 현재 상태를 유지한다. 단순히 `docker compose start`를
사용하는 것보다 Compose 파일 변경 사항까지 반영할 수 있으므로 이 프로젝트의 일상 실행 명령으로 `up -d`를 사용한다.

#### 특정 서비스만 시작하는 경우

```bash
docker compose -f infra/local/docker-compose.yml up -d mariadb
docker compose -f infra/local/docker-compose.yml up -d redis
```

마지막의 `mariadb`와 `redis`는 `container_name`이 아니라 Compose의 서비스명이다. `admin-core-be`를 정상 실행하려면
두 서비스가 모두 필요하므로 장애 확인이나 개별 재시작이 필요한 경우에만 나누어 실행한다.

#### Compose 파일 디렉터리에서 실행하는 경우

`infra/local`로 이동하면 현재 디렉터리에 `docker-compose.yml`이 있으므로 `-f`를 생략할 수 있다.

Windows:

```powershell
cd D:/workspace/admin-core-be/infra/local
docker compose up -d
docker compose ps
```

macOS:

```bash
cd ~/workspace/admin-core-be/infra/local
docker compose up -d
docker compose ps
```

두 방식은 같은 Compose 파일과 같은 컨테이너를 관리한다. 명령 실행 위치가 섞여 혼동되지 않도록 이 문서의 나머지
명령은 프로젝트 루트에서 `-f infra/local/docker-compose.yml`을 명시하는 방식으로 통일한다.

### 8.1 로컬 Profile과 환경 변수

|---|---|---|

| `ADMIN_FRONTEND_ORIGIN` | 선택 | 기본 `http://localhost:13010` |
| `ADMIN_CORE_DB_NAME` | 선택 | `admin_core` |
| `ADMIN_CORE_DB_USER` | 선택 | `admin_core` |
| `ADMIN_CORE_DB_PASSWORD` | 선택 | `admin_core` |
| `ADMIN_CORE_REDIS_HOST` | 선택 | `localhost` |
| `ADMIN_CORE_REDIS_PORT` | 선택 | `16380` |
| `SPRING_MAIL_HOST` | 필수 | 전달받은 팀에서 사용하는 SMTP 서버 주소 |
| `SPRING_MAIL_PORT` | 필수 | 해당 SMTP 서버의 전송 포트 |

| `SPRING_MAIL_PASSWORD` | 필수 | SMTP 로그인 비밀번호 |

### 8.2 Windows에서 bootRun

프로젝트 루트의 PowerShell에서 실행한다.

```powershell
$env:SPRING_PROFILES_ACTIVE='local'
$env:JWT_SECRET='replace-with-local-secret-at-least-32-characters'

$env:SPRING_MAIL_PORT='your-smtp-port'
$env:SPRING_MAIL_USERNAME='your-smtp-account'
$env:SPRING_MAIL_PASSWORD='your-smtp-password'

```

### 8.3 macOS에서 bootRun

프로젝트 루트의 Terminal에서 실행한다.

```bash
export SPRING_PROFILES_ACTIVE=local
export JWT_SECRET='replace-with-local-secret-at-least-32-characters'

export SPRING_MAIL_PASSWORD='your-smtp-password'

```

`bootRun`은 포그라운드로 실행된다. 이 Terminal을 닫지 말고 로그에서 애플리케이션 시작 완료를 확인한다. 코드나 설정을
변경해 재시작해야 하면 `Ctrl+C`로 애플리케이션만 종료한 후 다시 `bootRun`한다. MariaDB와 Redis 컨테이너는 계속
실행된다.

로컬 실행 시 다음 작업도 함께 수행된다.

1. `application.yml` 공통 설정을 읽고 `SPRING_MAIL_*` 환경 변수를 `spring.mail.*`에 바인딩한다.
2. `application-local.yml`이 로컬 DB, Redis, SQL 초기화와 쿠키 설정을 추가하거나 재정의한다.
3. `MailConfig`가 SMTP 설정을 적용한 `JavaMailSenderImpl` 빈을 생성한다.
4. `admin_core_schema.sql`을 MariaDB에 실행한다.
5. Hibernate `ddl-auto=validate`가 Entity와 DB 스키마를 검증한다.
6. API 서버는 `10086`, Actuator는 `11086` 포트에서 시작한다.

## 10. 초기 데이터와 최초 로그인

애플리케이션 시작 시 테이블 DDL은 자동으로 실행하지만 초기 역할, 사용자와 메뉴 권한은 자동 INSERT하지 않는다.
로그인하려면 [DB 정의서의 초기 데이터 INSERT 문](../db/DB_정의서.md#32-초기-데이터-insert-문)을 MariaDB에서
한 번 실행해야 한다.

DBeaver나 DataGrip 접속값:

| 항목 | 값 |
|---|---|
| DBMS | MariaDB |
| Host | `localhost` |
| Port | `13308` |
| Database | `admin_core` |
| Username | `admin_core` |
| Password | `admin_core` |

초기 SQL 실행 후 로컬 로그인 계정은 다음과 같다.

| 항목 | 값 |
|---|---|
| 로그인 ID | `master` |
| 초기 비밀번호 | `master` |
| OTP Secret | 최초 로그인 직후 새로 발급 |

이 계정은 로컬 초기 구동 전용이다. 운영 환경의 계정 생성 방식으로 사용하지 않는다.

## 11. OTP 메일을 포함한 로그인 테스트

OTP 메일은 별도의 활성화 여부를 두지 않고 항상 SMTP 어댑터를 사용한다. `application.yml`이 환경 변수를
`spring.mail` 설정으로 바인딩하고, `config.MailConfig`는 바인딩된 값을 읽어 `JavaMailSenderImpl` 빈을 생성한다.

```yaml
spring:
  mail:
    host: ${SPRING_MAIL_HOST}
    port: ${SPRING_MAIL_PORT}
    username: ${SPRING_MAIL_USERNAME}
    password: ${SPRING_MAIL_PASSWORD}
```

`MailConfig`에 명시된 값은 다음과 같다.

| 설정 | 값 또는 YAML 경로 | 설명 |
|---|---|---|
| Host | `spring.mail.host` | `SPRING_MAIL_HOST`에서 바인딩 |
| Port | `spring.mail.port` | `SPRING_MAIL_PORT`에서 바인딩 |
| Username | `spring.mail.username` | `SPRING_MAIL_USERNAME`에서 바인딩하며 발신 주소로도 사용 |
| Password | `spring.mail.password` | `SPRING_MAIL_PASSWORD`에서 바인딩 |
| Protocol | `smtp` | SMTP 전송 프로토콜 |
| SMTP Auth | `true` | 계정 인증 사용 |
| STARTTLS | `true` | 연결 후 TLS 전환 |
| Server identity check | `false` | 인증서의 서버 이름 검사 비활성화 |
| Debug | `true` | Jakarta Mail 디버그 로그 활성화 |
| SSL protocols | `TLSv1.2` | TLS 1.2 사용 |

YAML에는 환경 변수 바인딩 구조만 두고 특정 팀의 실제 Host, Port, 계정과 비밀번호는 작성하지 않는다. 프로젝트를
전달받은 팀이 애플리케이션 실행 전에 네 값을 모두 환경 변수나 IDE 실행 설정으로 전달한다.

Windows PowerShell:

```powershell
$env:SPRING_MAIL_HOST='your-smtp-host'
$env:SPRING_MAIL_PORT='your-smtp-port'
$env:SPRING_MAIL_USERNAME='your-smtp-account'
$env:SPRING_MAIL_PASSWORD='your-smtp-password'
.\gradlew.bat bootRun
```

macOS:

```bash
export SPRING_MAIL_HOST='your-smtp-host'
export SPRING_MAIL_PORT='your-smtp-port'
export SPRING_MAIL_USERNAME='your-smtp-account'
export SPRING_MAIL_PASSWORD='your-smtp-password'
./gradlew bootRun
```

`MailConfig`는 SMTP 인증과 STARTTLS를 활성화하고 TLS 1.2를 사용한다. 사용하는 메일 서버의 전송 방식이 다르면
Config의 SMTP 프로퍼티를 제공자의 요구사항에 맞게 변경해야 한다. 비밀번호와 실제 JWT Secret은 YAML이나 저장소에
작성하지 않고 환경 변수 또는 IDE의 로컬 실행 설정으로 관리한다.

최초 로그인 흐름:

```text
master / master 로그인
  ↓
Pre-Auth Token 발급
  ↓
OTP 바코드 발급 요청
  ↓
새 OTP Secret 생성 및 QR 메일 발송
  ↓
인증 앱으로 QR 등록
  ↓
현재 6자리 OTP 검증
  ↓
Access Token + HttpOnly Refresh Token Cookie
```

## 12. 로컬 CORS와 Cookie

기본 프론트엔드 Origin은 `http://localhost:13010`이다. 다른 주소를 사용한다면 `bootRun` 전에
`ADMIN_FRONTEND_ORIGIN`을 브라우저가 실제 전송하는 Origin과 정확히 같게 설정한다.

```text
올바름: http://localhost:13010
잘못됨: http://localhost:13010/
잘못됨: http://localhost:13010/admin
```

로컬 Profile은 HTTP 환경에서 Refresh Token을 테스트할 수 있도록 다음 값을 적용한다.

| Cookie 설정 | 로컬값 |
|---|---|
| 이름 | `admin_refresh_token` |
| HttpOnly | `true` |
| Secure | `false` |
| SameSite | `Strict` |
| Path | `/api/v1/auth` |

브라우저에서 Refresh와 로그아웃을 호출할 때는 `credentials: "include"`로 Cookie 전송을 허용하고,
`GET /api/v1/auth/csrf`에서 받은 토큰을 `X-XSRF-TOKEN` 헤더에 넣는다.

## 13. 종료와 재실행

### 13.1 애플리케이션만 종료

`bootRun`이 실행 중인 Terminal에서 `Ctrl+C`를 누른다. MariaDB와 Redis는 종료되지 않는다.

### 13.2 MariaDB와 Redis 종료

프로젝트 루트에서 실행한다.

```bash
docker compose -f infra/local/docker-compose.yml down
```

`down`은 컨테이너와 Compose 네트워크를 제거하지만 Named Volume의 DB·Redis 데이터는 보존한다.

### 13.3 다시 시작

```bash
docker compose -f infra/local/docker-compose.yml up -d
```

Volume이 남아 있으므로 이전 DB 데이터와 Redis 데이터가 다시 연결된다.

### 13.4 로컬 데이터를 완전히 초기화하는 경우

다음 명령은 이 프로젝트의 MariaDB와 Redis Named Volume을 함께 삭제한다. 로컬 데이터가 복구되지 않아도 되는 경우에만
Compose 파일 경로가 `infra/local/docker-compose.yml`인지 확인한 후 실행한다.

```bash
docker compose -f infra/local/docker-compose.yml down -v
```

다음 `up -d`에서는 빈 MariaDB와 Redis Volume을 새로 만든다. 애플리케이션을 다시 `bootRun`하면 DDL은 생성되지만
초기 계정 SQL은 다시 실행해야 한다.

## 14. 문제 해결

### Docker daemon에 연결할 수 없음

```text
Cannot connect to the Docker daemon
error during connect
```

- Docker Desktop이 실행 중인지 확인한다.
- Windows는 `wsl --status`로 WSL 2 상태를 확인한다.
- Docker Desktop의 Engine 시작이 끝난 후 `docker version`을 다시 실행한다.

### 포트가 이미 사용 중임

Windows:

```powershell
Get-NetTCPConnection -State Listen |
    Where-Object LocalPort -In 10086,11086,13308,16380
```

macOS:

```bash
lsof -nP -iTCP:10086 -iTCP:11086 -iTCP:13308 -iTCP:16380 -sTCP:LISTEN
```

기존 프로세스를 확인해 종료하거나 프로젝트 설정과 Compose 포트를 함께 변경한다. 한쪽 포트만 변경하면 애플리케이션이
DB 또는 Redis에 연결할 수 없다.

### MariaDB 또는 Redis가 healthy가 되지 않음

```bash
docker compose -f infra/local/docker-compose.yml ps
docker compose -f infra/local/docker-compose.yml logs mariadb
docker compose -f infra/local/docker-compose.yml logs redis
```

이전 MariaDB Volume은 최초 생성 당시의 계정과 비밀번호를 유지한다. Compose의 비밀번호만 바꿔도 기존 Volume의 계정은
자동 변경되지 않는다. 보존할 데이터가 있으면 DB에서 계정을 수정하고, 데이터가 필요 없는 완전 초기화일 때만
`down -v`를 사용한다.

### Gradle이 다른 Java 버전을 사용함

Windows:

```powershell
java -version
$env:JAVA_HOME
.\gradlew.bat --version
```

macOS:

```bash
java -version
echo "$JAVA_HOME"
./gradlew --version
```

세 결과가 모두 JDK 21을 가리키도록 수정한 후 Gradle Daemon을 종료하고 다시 실행한다.

Windows:

```powershell
.\gradlew.bat --stop
```

macOS:

```bash
./gradlew --stop
```

### 애플리케이션이 DB 또는 Redis에 연결하지 못함

1. `docker compose ... ps`에서 두 서비스가 `healthy`인지 확인한다.
2. MariaDB `13308`, Redis `16380` 포트가 열려 있는지 확인한다.
3. `SPRING_PROFILES_ACTIVE=local`인지 확인한다.
4. `application-local.yml`의 접속값을 임의로 변경하지 않았는지 확인한다.
5. 별도 환경 변수로 DB·Redis 접속값을 덮어쓰고 있지 않은지 확인한다.

### Swagger가 401을 반환함

현재 `SecurityConfig`는 `/api/docu`, `/api/docu/**`, `/api/swagger-ui/**`, `/api/v3/api-docs/**`를 공개한다.
애플리케이션을 재시작한 뒤 `http://localhost:10086/api/docu`로 접속한다. 이전 프로세스가 `10086` 포트에 남아 있지
않은지도 확인한다.
